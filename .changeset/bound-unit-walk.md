Bound the `IfcDerivedUnit -> IfcDerivedUnitElement -> Unit` walk in unit resolution, as the Rust resolver already is (#4603) (#7547). Behaviour changes:

- A derived unit that names itself, directly or through other derived units, no longer throws `RangeError: Maximum call stack size exceeded`. It threw from `extractProjectUnits`, `extractPropertiesOnDemand`, `extractQuantitiesOnDemand` and the readers built on them (the IDS bridge, rules). It is now unresolved, reported the way any unit these readers cannot resolve already is. A property's own `Unit` reads as its STEP reference with no scale, and a quantity's own unit as `explicitUnitUnresolved`. In the project assignment it is skipped, or kept declared without a scale when some of its elements composed (the existing "incomplete" rule, #4833). Rust skips it in both cases.
- On the parsed-source path, a chain of 16 or more nested derived units is now unresolved; 15 still resolve. Such a chain resolved before up to between 1,000 and 1,500 levels, depending on the stack, and threw `RangeError` beyond.
- On the parsed-source path, a derived unit is now unresolved, reported as above, once its charged entity reads pass 256 or read more than 64 KiB between them. Each read is charged before it is made, from the type the entity index gives. Inside the top-level unit, a read is free when the schema allows its type there: an `IfcDerivedUnitElement`, the `IfcNamedUnit` it names, and a conversion-based unit's `IfcMeasureWithUnit` and that measure's `IfcUnit`. Every other read is charged: a nested derived unit, every read below it, and any target the schema does not allow.
- On the parsed-source path, each free read is now made once per walk. A named unit's resolution, a conversion factor and its `UnitComponent` are kept by id, so 1,000 elements over one metre read it once, not 1,000 times. An element id that `Elements` lists again is charged, since a SET holds each member once. So the free reads of one walk parse at most twice the file size, plus the top-level unit's own reads (at most three records). Symbols and scales do not change: a unit's resolution depends on its id alone.
- So `main` resolved some units that are now refused. A fan-out of nested units took seconds there and composed a symbol exponential in its depth. A wide unit whose elements name nested units is refused too. Other units outside the schema are refused once they need more than 256 charged reads, or 64 KiB of them. That covers elements whose `Unit` is an `IfcMonetaryUnit`, and an `Elements` list that repeats one element more than 256 times. It covers conversion factors that are not an `IfcMeasureWithUnit`, where `main` used the name's known factor. And it covers factors whose `UnitComponent` is not a unit, which `main` took at 1.0.
- Elements that are not `IfcDerivedUnitElement`s, or whose `Unit` is not a unit at all, never resolved. `main` read their target once per element, so a wide unit over one large entity cost its width times that entity's size. Those reads are now charged too.
- A derived unit whose composed symbol passes the engine's string limit is now unresolved, reported as above. `main` threw `RangeError: Invalid string length`. `IfcLabel` has no length limit in IFC2X3, so a schema-valid 305 KB file reaches it: 2,700 elements over one unit with a 200,000-character name. On the native path of `extractProjectUnits` this is the existing `Native project unit is unresolved or unsupported` refusal.
- Unchanged: a flat derived unit, as the schema types it, is never charged and resolves at any width with the same symbol and scale as before (`Elements` is `SET [1:?]`). A dangling reference reads nothing and costs nothing. Nothing is kept between walks, as on `main` and in Rust, so N references to one unit cost N walks. The Rust resolver charges every read, so there a flat unit of 128 or more SI elements is refused, as it already was.
- The native read path keeps its walk from `main`. The depth cap, the budget and the memo do not apply there, and its path set refuses a cycle as before. Its callers' 512-read limit and their `exceed the read limit` refusal (#7353) bound it, a chain of nested units included.
