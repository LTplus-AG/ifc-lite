Make the CSV formula-injection guard (CWE-1236) one shared function instead of five copies, and close the three call sites the #1944 hardening never reached. `bim.export.csv()`, `ifc-lite export --format csv`, the CLI and MCP headless backends' `export.csv`, and the viewer's export adapter each carried their own `escapeCsv`. Only the SDK namespace's copy looked for the formula trigger PAST leading invisible characters, so an entity name of `<BOM>=HYPERLINK("http://evil")` — which a spreadsheet still evaluates, and which an IFC file can carry via the `\X2\FEFF\X0\` escape — was exported guarded through the SDK and UNGUARDED through the CLI, the MCP server and the viewer adapter. Nothing enforced the agreement: deleting the guard outright from any of those three left all of their tests green (435 CLI, 272 MCP). `ifc-lite export --format csv` diverged from itself as well, since `--columns Name` escaped through the SDK namespace while `--columns Name,Pset_X.Y` escaped through the CLI's own weaker copy. All five now call `escapeCsvCell`, newly exported from `@ifc-lite/sdk`, whose invisible-prefix class is also widened from `\p{Zs}` to `\p{Z}` so U+2028/U+2029 — matched by neither the old guard nor the `\n`/`\r` quoting check — cannot serve as the hiding prefix either. Benign cells are untouched, and a leading TAB or CR is still a trigger in its own right rather than skippable whitespace. New tests drive the guard end-to-end through both of the CLI's column paths and through the viewer adapter's real `csv()`, and pin the shared helper directly. The deliberate, separately-tested disagreement between `@ifc-lite/lists`' `listResultToCSV` (which exempts a plain number from the `-`/`+` trigger) and the viewer's Lists exporter (which does not) is a product decision and is left as it stands.
