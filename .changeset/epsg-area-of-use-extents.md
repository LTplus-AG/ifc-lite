The bundled EPSG data now carries each CRS's area of use, native units and compound components, so headless checks can tell when coordinates lie outside the CRS they claim. The data is a separate lazily loaded module (about 59 KB gzipped, loaded only on first use) and the search index itself is unchanged. New exports: `getEpsgAreaOfUse` / `getEpsgAreasOfUse` (WGS84 bounding box, `west > east` with `crossesAntimeridian` for extents that cross the date line), `getEpsgUnits` (separate horizontal and vertical unit, name and metres per unit), `getEpsgCompoundComponents`, `isLonLatInAreaOfUse` / `isLonLatInEpsgAreaOfUse` (degree margin, antimeridian-aware, `|lat| > 90` and non-finite input are outside, a negative margin throws), `loadEpsgExtentsFetchedDate` / `loadEpsgExtentsDatasetVersion`, and `createEpsgCrsCatalog()`, a synchronous `lookup(code)` / `resolveName(name)` catalog whose area of use is the hull of all current usages and carries `crossesAntimeridian` and a wrap-aware `contains(lon, lat, margin?)`. The extents come from EPSG dataset 13.106 while the main index is 12.054; the licence notice and the exact transformations applied are in the package README. `@ifc-lite/data` is now marked `sideEffects: false`. Regenerate with `pnpm generate:epsg-extents`.
