An entity facet whose name lists the same class more than once (an `xs:enumeration` such as IFCWALL, IFCWALL) now selects each entity once (#ISSUE). The class's ids were collected once per listed value, so every instance was a candidate twice: `applicableCount`, `passedCount`, `failedCount` and the report summary's totals counted it twice, `entityResults` held two rows for it (so `createBCFFromIDSReport` wrote two topics per failing entity), a prohibited specification failed it twice, `minOccurs`/`maxOccurs` were checked against the doubled count (three walls passed `minOccurs="4"` and failed `maxOccurs="5"`), and repeats used up `maxEntities` (with IFCWALL, IFCWALL, IFCDOOR and a limit of 4, one wall was checked twice and no door at all). `passRate` changes only where the doubling skewed it: a list mixing repeated and once-listed classes, or a cardinality verdict that flips. The exported `filterByEntityFacet` and `filterByFacet` now return each id once for such a list, in first-listed order, also when a repeat differs only in case or when an accessor's type lists overlap. With `createDataAccessor`, or any accessor whose type lists do not overlap, a list of distinct classes returns the same ids in the same order as before; a simple value, an `xs:pattern` and the IFC2X3 mapping-alias full scan are unchanged.
