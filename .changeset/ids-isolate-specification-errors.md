One specification that throws no longer ends the whole `validateIDS` run (#7482). Only a rejected `xs:pattern` (`UnsafeRegexPatternError`) used to be caught per specification; any other error rejected the run and discarded every other specification's verdict. Now an error from evaluating a specification fails that specification with `error: "Specification could not be evaluated: <reason>"`, as a rejected pattern always did, and the other specifications are reported, as `runRuleSet` in `@ifc-lite/rules` already does. A host's cancellation (anything thrown with the name `AbortError`) and an exception thrown by the host's own `onProgress` callback still end the run, so a host callback failure is never reported as a specification verdict. The applicability property index that the specifications of a run share now marks an entity as indexed only once its property sets are folded in, so an entity whose sets could not be read is not silently left out of a later specification. A specification with `error` set is an evaluation error, not a `fail` verdict: the buildingSMART corpus, preview, writer round-trip and IfcTester parity tests, the conformance and AI-eval scorers, and `ifc-lite delivery` (whose IDS check now reports `error`, with `erroredSpecifications` and the reasons, as its rules check already does) all treat it so.
