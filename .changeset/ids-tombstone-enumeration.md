`createDataAccessor`'s entity-enumeration methods enumerated a `store.removeEntity()`-deleted entity for IDS validation — a conformance validator counting, applying requirements to, and reporting on an element the caller had deleted. `createDataAccessor` now takes an optional third `entityVisibility` argument (`EntityVisibilityView`, satisfied structurally by a `MutablePropertyView`), consulted by **both** `getAllEntityIds()` and `getEntitiesByType()`: each excludes tombstoned entities, and `getAllEntityIds()` additionally includes overlay-created entities still alive (`getEntitiesByType()` cannot, since nothing in this accessor resolves a created entity's type — a known, separate gap). `getEntitiesByType()` is the dominant path in practice: any IDS specification whose applicability names an entity type directly (`<entity><name><simpleValue>IFCWALL</simpleValue></name></entity>`, or an `<xs:enumeration>` of several types) resolves through it, not through `getAllEntityIds()`, which only a specification with no entity facet at all (or a regex entity name) falls back to. The IFC2X3 mapped-alias case (an IDS facet naming an IFC4-only class IFC2X3 represents via an occurrence/type pairing, e.g. `IFCAIRTERMINAL`) already fell back to a full scan through `getAllEntityIds()` and needed no change. Every existing call — including every call with no third argument — is unaffected: `createDataAccessor(store)` and `createDataAccessor(store, propertyOverlay)` behave exactly as before.

The MCP server's `ids_validate` tool now passes its model's mutation view, so a session that deletes an entity and then re-runs IDS validation gets the corrected `applicableCount` and cardinality result, for both the no-entity-facet case and the far more common entity-typed case. The viewer's IDS validation (main-thread and worker) already picked this up through the same wiring.
