The byte reader that builds the relationship graph now records no edges for a relationship record it cannot read cleanly, instead of part of one (#9192). A nested or typed value in a related list (`((#10),#14)`, `(#10,IFCLABEL('x'),#14)`) used to end the list early and shift the rest into the relating slot, so `#14` became the relating entity of `#10` for every consumer of the graph: spatial containment, aggregation, voids, typing, property and quantity lookups. A record is now skipped when its related list, or a property definition set, is not a plain comma-separated list of references (empty `$` members are still allowed; `((#24),#41)` and `(#24,'x')` are skipped rather than read as `#41` or `#24`), when a relating value other than a property definition set names more than one entity (`(#40,#41)`, including a material, classification or document association), or when a value is followed by anything other than the next attribute or, for the last attribute, the record's own closing `)`. Property set definition sets stay valid in both spellings, `(#24,#41)` and `IFCPROPERTYSETDEFINITIONSET((#24,#41))`. Valid files produce the same graph as before. One consequence for the type-quantities read: a related list mixing references with a string or a number (`(#10,'x',#14)`) now refuses the whole model, as a read of every relationship does, rather than only the elements it names, because a string such as `'#14'` or a number decodes as a reference the graph could not see. The first-selection type-quantities read no longer needs its own guards against such records: they had answered some elements differently from a read of every relationship, depending on which element was selected first.
