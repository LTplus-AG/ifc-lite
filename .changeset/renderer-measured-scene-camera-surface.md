"@ifc-lite/renderer": major
---

**BREAKING.** `Renderer.getScene()` and `Renderer.getCamera()` now return the measured interfaces `SceneContents` and `CameraControl` instead of the `Scene` and `Camera` classes, and `Renderer.getRaycaster()` / `Renderer.getSnapDetector()` are removed.

`Renderer` published 70 methods, and six of them handed the implementation straight across the package boundary. `getScene()` returned `Scene` (4,429 lines) and `getCamera()` returned `Camera`, so the interface a consumer had to learn was `Renderer` plus the whole of both classes, and every method added to either one silently became published API of `@ifc-lite/renderer`. That is the definition of a shallow module: an interface about as complex as the implementation behind it.

The two accessors now return interfaces naming only the members that are actually reached from outside the package. `SceneContents` has 46 members, `CameraControl` has 39. Both are exported from the package root, so a consumer can name the type it is holding.

The member lists are a measurement, not a design sketch. Every `renderer.getScene()` / `renderer.getCamera()` call site in `apps/viewer` and `apps/viewer-embed` was resolved with the TypeScript checker and the returned value followed through locals, class fields, object-literal properties, parameters and named-function returns until it was dereferenced: 125 call sites in total, with no unfollowable escapes. A second, independent type-directed sweep over every property access whose object type resolves to `Scene` or `Camera` agreed exactly on `Camera` (39 of 39) and found one extra `Scene` member the flow scan structurally cannot see (a scene passed to a parameter typed as a caller-side structural interface), which is included. Neither `Scene` nor `Camera` gained an `implements` clause: an `implements` clause would let the class's surface drift wider again without the interface noticing, so the check that the classes still satisfy these shapes is the `return` inside each accessor, which stops compiling the moment a signature diverges.

`getRaycaster()` and `getSnapDetector()` are gone. Both were dead: a repo-wide search, including the aliasing forms a plain identifier search misses (`renderer['getRaycaster']`, `.bind`, destructuring off a `Renderer`), found no caller anywhere. `RaycastEngine` is still exported and still has `getRaycaster()` / `getSnapDetector()`, so a consumer that needs either instance can reach it through the engine.

`getPipeline()` and `getGPUDevice()` are deliberately NOT narrowed, and it is worth saying why rather than inventing a narrowing that merely looks like the other two. The same scan found zero `RenderPipeline` members and exactly one `GPUDevice` member (`queue`, for `queue.onSubmittedWorkDone()`) reached from outside the package: every other call site takes the handle, null-checks it, and passes it back into a `SceneContents` upload method typed for the real `GPUDevice` and `RenderPipeline`. A narrower return type there would break those call sites and buy nothing. It would be a brand rather than a measurement, and would only become honest if `Scene`'s own parameter types were narrowed too. `GPUDevice` is in any case a WebGPU standard type this package neither owns nor grows, so it is not a surface that can drift.

**Migrating.** Code that only calls methods on the value it gets back needs no change. Code that annotates the value as `Scene` or `Camera` should annotate it as `SceneContents` or `CameraControl`; that was the single break inside this repository. Code that needs a member absent from these interfaces has found a gap in the measurement, so please open an issue naming the member: adding one is a published-API decision rather than a detail, and each interface's module doc says so at the top.
