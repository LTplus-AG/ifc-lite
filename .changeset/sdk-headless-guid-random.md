`HeadlessBackendOptions.guidRandom` (also `openModel(bytes, { backend: { guidRandom } })`) seeds every GlobalId a headless session authors. Fresh sessions with the same model and seed produce the same IFC `DATA` section when edits and exports run in the same order. Each export that generates property sets advances the random source, so repeated exports in one session can produce different GlobalIds for those property sets. `@ifc-lite/create` already took a seeded `SpatialAnchor.guidRandom`, but the SDK never passed one: it now rides on the model resolution (`CostStoreModelResolution.guidRandom`) into every anchor the store backends resolve, into copy, duplicate, array, mirror, split (joins included), trim and extend, retype layer usages, classification, room create and edit, roof, storey add and storey delete, and structural derivation. The seed also reaches the property sets `export.ifc()` writes. The create operations that resolved their own anchor or wrote GlobalIds without one (`addHostedElementInStore`, `addStoreyInStore`, `applyStoreyDelete`, `reassignElementsToStoreyInStore`, `mirrorElementsInStore`, `copyToStoreysInStore`, `addClassificationInStore`, `assignClassificationInStore`, `createRoomsInStore`, `syncRoomLayoutInStore`, `editFootprintRoofInStore`, `trimExtendElementInStore`) take a trailing optional `AuthoringGuidOptions`, `EditTarget` takes `guidRandom` (so edits that re-create wall joins, such as move, resize and wall section, and layer-usage splits on retype are seeded), `resolveWallJoinAnchor` takes it as a third argument, `ElementSplitOptions` takes `guidRandom`, `CopyBatchOptions` takes `guidRandom` beside `duplicate`, so a seeded copy, array or storey copy keeps the source Name and only an explicit `duplicate` renames it, and `GroupStoreContext` takes `guidRandom`. Shared store backends that support structural relationship operations also use the seed for those operations. Omitting `guidRandom` uses the platform CSPRNG when Web Crypto is available and falls back to `Math.random` otherwise.
