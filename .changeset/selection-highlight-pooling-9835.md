Orbiting with a large selection is no longer slow (#9835). The highlight of a selection used to be one GPU mesh per selected piece, each with its own uniform write and three draws on every frame, and every frame also rebuilt the selected-id set and looked up each selected entity's pieces. Selecting all 16,916 elements of a 326 MB model took a frame from 4 ms to over 400 ms of renderer time and from 1,099 to 31,541 draw calls. A selection whose highlight copies would pass the 500-piece pick budget now pools into merged meshes that retain the per-piece hydration insertion order through selection changes and hide/isolate, one per run of pieces sharing a model and frame origin (the per-entity merge of #9192, across entities), and the renderer keeps the selection's highlight meshes between frames, redoing them only when the selection, hide/isolate, the model or item scope, or the scene's geometry changes. The highlight itself is drawn from the same vertices by the same pipeline as before. `RenderOptions.selectedIds` is still compared by content on every frame (one lookup per id, no copy), so a new Set and any in-place edit are seen on the next frame as before; only a frame rendered with `isInteracting` re-reads at most 32,768 ids, so swapping ids in place at the same count in a larger Set is seen within a few interactive frames.

Pooled highlights no longer reorder overlapping selected surfaces after hide, isolate or half-selection changes. The old regrouping fallback beyond 500 runs is removed: interleaved models or origins draw once per run, reaching but never exceeding the per-piece cost. Incompatible per-piece origins retain the documented #9946 limitation; bounded, order-preserving interleaved-frame pooling is tracked in #10008.
