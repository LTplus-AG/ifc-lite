A model loaded through the processing server no longer blanks the page when its properties arrive. The viewer registers such a model from its meshes and receives the data model afterwards; an entity without geometry (a storey, a space, a type) whose id lies above every meshed id was then outside the model's published id range, and the first lookup threw `[FederationRegistry] Local ID N is not published`. `FederationRegistry.extendModel(modelId, maxExpressId)` grows a fully published model's range in place and returns the highest published id; the viewer calls it when the server's data model is swapped in, and the model's `maxExpressId` follows. The offset never moves. A model with a later neighbour grows to the end of its overlay headroom, its `maxExpressId` is that end so it never claims the later model's ids, ids beyond it stay unresolvable and are reported, and editing that model is refused, since its authored ids would collide with the later model. Editing a server-loaded model is refused while its properties load or after they failed ("The model's properties are still loading"), so no authored id can collide with a hydrated one; a range that carries authored ids is refused rather than aliased.

The viewer uses `FederationRegistry.hasOverlayCapacity(modelId, nextLocalId, count = 1)` and `subscribe(listener)` to keep allocation permissions current without requiring earlier lazy creations to be published. `canPublishOverlayFrom` checks the next contiguous publication only; using it as an allocation permission would lock a model after one lazy `addEntity`. All reservations, including the newest model, cap allocation at their reserved overlay headroom and the global safe ID limit, so later model loads cannot steal unpublished authored IDs. Registry publication and preview throw `OverlayIdSpaceExhaustedError` (`reason: 'id-space-exhausted'`) for an oversized contiguous batch, with contiguity errors first. The exported `ModelRange` type is unchanged.

Pass `view.highestAuthoredExpressId(maxExpressId)` as the optional third argument of `extendModel`: this includes live, deleted, forgotten and stashed/undoable IDs at or below the requested source maximum, without mistaking source allocator floors for authorship. The ceiling prevents a higher creation from masking a lower collision. Refuse only claims in the source growth interval; retained creations above the new maximum remain unpublished/publishable across clear/reload. Every allocating viewer mutation view, including cold planners, receives the same source and permanent ownership floor at construction. The mutations package exports `highestExistingExpressId(store)`, the source watermark used by `StoreEditor`. Hydration commits source data, ownership bounds and capacity together, including superseded settlement. Allocator notifications observe complete creation, `restoreNewEntity` (including unstashed edits/indexes) and restored transaction state, reentrant capacity changes drain to stability, and allocator ticks refresh only their model. Refusal messages cover both oversized stores and exhausted edit headroom.

Source-only views and their cached editors are dropped in one store commit on full model clear, so a reloaded model starts from its new registration floor; pending edits remain retained. A refused re-hydration keeps the previous store and restores only settled previous runs; an ownerless running/cancelled run becomes a failed refusal. The activity tray records the refusal as a failure, never completion. Read-only facades avoid allocator configuration, and the shared source watermark uses compact maxima and deferred IDs without scanning compact keys or redundant compact-store entity columns; table-only IDs remain covered for map/indexless stores. Invalid overlay ranges keep their generic validation errors; only insufficient capacity reports ID-space exhaustion.
