Fix `dayPath`, `analemmaPaths`, and `domeGraticule` failing silently on a non-positive, `NaN`, or too-small step option. Each function drives a `for (...; x += step)` loop from a caller-supplied option — `stepMinutes`, `dayStep`, `altitudeStep`, `azimuthStep`, `resolution` — none of which were validated. A value of `0` (or negative) left the loop variable unchanged forever, blocking the process with no error — confirmed live: `dayPath(date, lat, lon, { stepMinutes: 0 })` did not return within an external 5-second `timeout` wrapper before this fix. `NaN` does not hang: `x += NaN` makes the loop variable `NaN`, and the next bound comparison is then always false, so the loop exits after a single iteration instead of running forever — a truncated result, not a hang.

All five options now throw a descriptive `Error` synchronously when the value is not finite or not `> 0`, instead of failing silently. All five also reject a positive value too small to actually advance the loop at its upper bound (e.g. `Number.MIN_VALUE`, or `1e-15`, where floating-point addition can leave `bound + step === bound` unchanged) — the same hang reached through a different input. `altitudeStep` and `resolution` initially shipped with only the `> 0` check and no progress test, which left this exact gap reachable via `domeGraticule({ resolution: 1e-15 })` / `{ altitudeStep: 1e-15 }`; they now use the same `bound + step === bound` guard as the other three, checked against the largest-magnitude bound each option's loop actually reaches (90° for `altitudeStep`, 360° for `resolution`, since `resolution` also drives a 90°-bound loop and the 360° check is the stricter of the two). Valid (positive, sufficiently large) values behave exactly as before.
