Fixed a TS/Rust STEP scanner divergence (#3733): a form feed (`0x0C`) or vertical tab (`0x0B`) between STEP tokens was not treated as trivia by `isSpaceByte`/`skipTrivia` in `packages/parser/src/step-lexing.ts`, and the same gap existed in every hand-duplicated copy of that byte set — the inline fast path in `StepTokenizer.scanEntitiesFast`, the Blob-worker scanner, and the entity-index-to-refs fast path that reads a type name out of a pre-computed byte span. On a source carrying one of these bytes, `scanEntities`/`scanEntitiesFast`/the worker silently dropped the entity outright, or `buildEntityRefsFromIndex` produced a type name with the stray control byte still attached, while Rust's `EntityScanner` parsed the same file correctly — same file, different answer depending on which engine ran.

The project already resolved this exact question once, for the HEADER-section scanner (`StepTextScan.isAsciiSpace` / `rust/export/src/source_header.rs`'s `is_step_space`): both spell out the full six-byte ASCII whitespace set (space, tab, LF, CR, form feed, vertical tab) rather than trust a stdlib "ASCII whitespace" helper, after a prior regression where doing exactly that mismatched the two halves on vertical tab. `isSpaceByte` and its TS-side duplicates now carry that same six-byte set, and `rust/core/src/parser/lexical.rs::skip_step_trivia` no longer calls `u8::is_ascii_whitespace` (which follows the WhatWG set and excludes vertical tab) — it now shares a spelled-out `is_step_space` with the same six bytes, also used by `EntityScanner`'s type-name boundary check in `scanner.rs`.
