## Two concrete source-level caveats

### New per-operation schema allocation

`program/boolean/work.rs:16-21` constructs `BooleanClippingProcessor::new()` for every `Execute::execute`, even constructor evaluation, prism construction and shell evaluation whose implementation ignores the recorder. `processors/boolean/mod.rs:81-95` initializes `IfcSchema::new()`. `core/src/schema_gen.rs:397-406` and following lines show this allocates and populates two HashMaps. Baseline performed those numerical operations on the existing recorder or directly evaluated the admitted constructor/shell; it did not instantiate another schema per numerical operation.

This is a concrete additional hot-path allocation mechanism, not a measured latency/RSS regression. A smaller failure-only sink, or explicit no-effects execution for operations that cannot produce Boolean records, would avoid carrying source-dispatch schema into this numerical effect domain. Any change should retain operation-specific flags in payloads and actual recorder publication order. At minimum the eventual end-to-end allocation/perf qualification must include this mechanism; allocation neutrality is not supported by source inspection.

### Moved caller path has no unwind restoration

`program/boolean/mod.rs:169-174` takes the caller's entire `OperandPath` and restores it only after `program.run` returns. If unwinding crosses that call, the caller retains a fresh empty default while the old memberships and spent monotonic visit count are dropped. The baseline Driver borrowed the caller's path, so unwind did not reset ancestors or spent visits (baseline itself did not clean newly active memberships on panic either). Normal `Ok` and `Err` restore the owned path and remove this child's active entries correctly.

This is a structural unwind difference; I have not demonstrated a genuine source input that triggers a caught panic in these fresh built-in paths, and do not present one as a geometry failure. If the stated preservation contract includes a caller catching internal unwind and resuming with the same path/budget, restoration needs RAII. A targeted invariant would seed an ancestor and spent visit, induce an unwind at a real reached admission/evaluation boundary with a scoped test hook, catch it, and show the ancestor and spent count survive. This must not assert that baseline cleaned its own active entries, which it did not.

The new temporary effect sink similarly transfers records on returned errors but not unwind: a fallback record written before a panicking plane evaluation would be lost with the private sink. That distinction is relevant only if panic-retained diagnostic evidence is promised; no real numerical panic reproduction was executed here.

## Boundary and terminal-resource scope

The private BooleanProgram is currently synchronously driven to completion by `run`, and `Services` is passed through its loop. It does not yet yield typed source requests to a unified public ProductProgram polling executor. Its frames nevertheless contain genuine owned control rather than decoder callbacks. `Completed<P>` enforces consuming result-class typing; it supplies no request-instance, source epoch, runtime slot generation, recorder identity or cross-session acceptance authentication. Current direct call sites immediately assemble into the actual recorder, which makes that limitation explicit rather than unsafe detached scheduling.

Typed `ResourceRefused`/`Cancelled` integration is not implemented in this separate child. Existing historical catches remain broad: `step.rs` catches bounded-prism lowering/evaluation failure for plane fallback; `batch.rs::prepare_group` catches plane/lowering/prism refusal and rewinds; `operand.rs::without_voids` converts shell errors to one source-loss record. When the resource implementation is joined, terminal stops must propagate past every one of those catches before historical recovery. A sticky enclosing account must also prevent successful publication if a legacy callback catches a terminal internally. The current patch does not claim resource safety, so these are mandatory integration points, not evidence that an absent resource error was already swallowed.
