## Remaining concrete blocker: new native multi-product fixture retains exclusive leases

processing/session_retained/mapping_tests.rs constructs one decoder/router for each product-count/mode scenario, keeps completed executions in `completed` (lines110–150), and calls RetainedProductExecution::new repeatedly with that same owner pair (product loop line124; later type job line163). RetainedProductExecution owns ProductState.owner. ProductOwner contains the exclusive decoder/router ExecutionLease values (session_owner.rs16–26). Neither retained completion branch in session_retained.rs149–183 releases that owner: it stores the plan/stage but retains the entire ProductState. `completed.push(execution)` therefore keeps the original reservation alive.

Consequences: products1 succeeds its product construction then fails type-executor construction with OwnerBusy; products3 fails the second product's constructor. The asserted direct volumes28/4/0 and final N-product checks are not reached for those scenarios. The exact SDK runtime is not needed to infer this ownership failure, though the fixture conditionally skips without it. Dropping completed executors is not a valid quick fix because their original receipts currently retire the shared worker, the separately tracked lifetime issue.

Small test-only correction: give each retained product executor and the later type executor a distinct actual bound decoder/router pair from the SAME model SourceBundle and identical explicit instancing configuration, keeping those pairs alive with their executions as needed. The test can still derive actual relation/reference facts from the common source and compare distinct product placements/slots, while avoiding an unauthorized second reservation. If production is intended to retain a completed execution while reusing its original decoder/router, that requires an explicit reviewed release-at-completion ownership contract, not weakening try_lease or implicit reentrancy. This review does not authorize that broader change.
