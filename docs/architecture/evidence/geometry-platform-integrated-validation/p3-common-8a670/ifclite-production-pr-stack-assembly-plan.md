## Assembly method

Build each eventual slice from the pinned final implementation's relevant hunks and tests, against its explicit immediate parent. Do not cherry-pick the foundation checkpoints or merge commit55f as landing units. Do not copy a whole lib.rs/mod.rs/Cargo.toml/ratchet file from the integration head: its imports and registrations include later layers. Add just the declarations, variants and actual gateway consumers introduced in that slice. Carry ratchet reductions only when their owning code has actually moved. No allowance increases to accommodate a split.

Producer extraction detail: final processor files already include `lower_owned`/`lower_program` trait hooks referencing the final `OwnedConstructor`/`GeometryProgram` enums. B1–B6 must initially carry their concrete private plan plus the existing `process` -> lower/evaluate delegation, not those later registry hooks. Add the hooks, trait surface and enum arms together with the actual graph/item consumer inC1/D2. Otherwise the apparently small producer PR imports the entire common program and inverts the proposed dependency order. This is a hunk reconstruction requirement, not permission to leave an unused alternate plan.

Resource extraction detail: D1 can add concrete preflight/retained cache ownership to the still-existing canonical router mapping code, thenD3 replaces that walk while retaining the same helper/account semantics. If doing so would require a second algorithm or rollback-only compatibility path, merge that specific cache consumer hunk intoD3 instead of inventing an intermediate implementation; explicitly disclose the resulting atomic size.

Each slice must actually use its new seam in the existing canonical path and delete the superseded implementation in the same PR. Introducing a parallel whole-product implementation to get smaller diffs is unacceptable. An explicitly private standalone runtime or source-neutral imported crate can land before product integration if its actual public/consumer contract, isolated tests and refusal limits are clear; that does not qualify final products.

Target roughly1,500 changed handwritten source/test lines per review. Sizes below are measured groups or initial packing targets, not certified final diff sizes. Generated artifacts and compact provenance belong in the matching behavioral PR, not a fake artifact-only review later. Where one atomic control cutover cannot fit, make its numerical/source seams independently consumed first, then explicitly review the remaining larger cutover. Never split an enum from required variants or a consumer from required producer imports merely by folder.

At stack creation inspect the live rulesets using the existing authenticated repository API and compare their exact required contexts to .github/workflows; this read-only planning task did not query or assert the live rule list.
