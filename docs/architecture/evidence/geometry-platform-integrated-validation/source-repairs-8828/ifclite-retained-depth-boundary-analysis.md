# Retained depth boundary: correction and implementation decision

Source scope: `8828c182856bdb150c9b0d2146b36162b6d96b98`. Read-only source analysis; no repository edits, builds, executable probes or jobs. No actual accepted-exact/current-retained-refused counterexample was established. Therefore this report corrects the earlier broad “mixeddepth32 no-loss gap” label to an **unqualified preservation candidate**, not a demonstrated exact regression. It supersedes that label in earlier reviews without rewriting their frozen records. No bound should be raised on the evidence available here.

## Pure42 Boolean chains are a different path

The shared path does not gain one child entry per FirstOperand Boolean. `boolean/batch.rs11–28,75–85` uses the owned iterative Walk.spine/seen structure; NextFirst changes current and pushes another owned Walk frame. The retained path takes the same NextFirst route. `BooleanState::enter_boolean` handles the actual nested operand entrance and preserves existing OperandPath visit/path/depth accounting. Spine length itself does not become nesting depth.

`item.rs`'s execute_retained lower_program branch explicitly assigns `child.retained_walk = retained_walk::current()` because that Boolean program is the SAME occurrence. It does not call RetainedWalk::child for every spine node. From a product, the root and selected plain Boolean item consume shared path entries; the Boolean wrapper reuses that path. Forty-two left-spine nodes therefore do not imply forty-two shared ancestry entries or a depth32 refusal. CSG control is likewise already handled by the existing Boolean frames/path, not automatically another shared child.

The exact tree already has meaningful preserved baselines in `processors/boolean/chain_cycle_tests.rs`: the1000-node collector fixture verifies iterative collection, while deep_left_difference_chain_resolves_past_depth_cap constructs a14-step real solid Difference chain, checks nonempty output/bounds and documents the Revit42-node history. The collector's invalid placeholder solids are NOT a numerical thousand-operation preservation oracle. Extending the real solid witness to42 and pairing exact output with retained admission/runtime is the right execution request; no current run or new accepted source fixture is asserted here.

## Mapping tiers are not every shared child either

Normal nested mapped items inside one MergedWalk/SubmeshWalk are owned Enter/Exit frames with their existing depth counter and path set, not recursive retained_item calls. MergedWalk increments depth for nested mapped items; SubmeshWalk additionally applies its existing depth rule to the plain child. The existing mapping test maximum_depth_applies_to_plain_submesh_children_but_not_merged_source_leaves deliberately demonstrates this consumer distinction at32. A replacement must preserve that distinction rather than interpreting32 as an interchangeable universal nesting count.

Only a reached plain item returned from mapping forks GeometryProgram::retained_item (`inner_mapping.rs107,117`). A mapped operand inside retained Boolean forks retained_mapped (`boolean/operand.rs17–22`). Thus alternating Mapping→plain Boolean→mapped operand is the obvious way to grow the shared mixed path. The shared cap is real for that newly admitted class, but that fact alone does not prove an old exact-input loss.

## Why the tempting alternating counterexample is invalid as a baseline

The actual exact Boolean operand branch is different: mapped-child dispatch exists ONLY under self.retained. Outside it, builtin_processor must provide a supported owned constructor; processor_registry.rs's declared families contain no IfcMappedItem. The fallback records UnsupportedOperand(IfcMappedItem) and supplies empty geometry. A16-tier mapping/Boolean alternating graph can consequently hit the shared32 path with fewer than32 mapping tiers and few Boolean visits, yet cannot honestly be described as fully supported/accepted exact geometry.

In particular, repeated coincident-box UNIONs can hide this exact unsupported-operand loss: the other operand alone still produces a nonempty box with the same volume. Nonempty output or that coincident volume is insufficient to establish preservation. A future differential witness must require zero dropped-source/UnsupportedOperand diagnostics and independently distinguish every operand contribution, for example by disjoint placements and volume/component/receipt expectations. This report supplies no fabricated “accepted exact” repro from that case.

## Concrete next steps

1. Add/execute the paired real42-step solid-spine witness using the existing actual extrusion/cutter source construction. Confirm exact geometry, bounds/volume/closure and zero relevant failures; retained logical admission must produce every reached construction/operation without a shared Representation stop. Actual target runtime then verifies its own result. Keep final-product closure claims separate. Test32-tier merged and31-tier styled mapped wrappers around a legal Boolean leaf under each consumer's existing boundary; do not use a pre-existing styled32 refusal as a regression.
2. Keep the current mixed guard and mark its unqualified candidate boundary explicitly until a genuinely supported exact witness demonstrates loss, or the product program explicitly promises a broader newly supported mixed class. Existing mixed cycles and adversarial DAG tests remain required. No blanket cap increase, global visited set, exact fallback or source preclassification closes this requirement.
3. If a broader mixed class must be admitted, first separate semantic source ancestry from execution-stack depth. Introduce typed edge provenance at the existing retained_entries constructors: same-occurrence wrapper (no new source node), mapped occurrence, type-map source, and plain/Boolean item. Preserve cycle detection over the full active mixed source ancestry; preserve DAG multiplicity by restoring it on exit. Mapping's existing per-controller depth rules and Boolean's iterative spine/OperandPath policies remain authoritative for their domains. A generic Vec length must not replace either historical rule.
4. Before removing the combined stack guard, make the existing common child protocol iterative end to end. The seam is GeometryProgram's active child in Item/Mapping/TypeMap/Boolean/Product adapters. Use an internal stack of those same owned continuation frames to trampoline request, execute/take_ready, reply validation/acceptance, cancellation/report draining and destruction; do not add a second source walker or executor. Recursive validate/cancel/Drop are stack risks even if polling is iterative. Preserve linear request/reply tickets and all original source/router/processor bindings.
5. Keep a shared monotonic work limit and account real source entry, source-frame storage, cache scans, value expansion, copy/history/presentation and path membership/copy costs. Removing a length cap while cloning an ever-growing Vec on every child would permit quadratic work/memory before the existing entry budget expires. Either budget those scans/copies or use persistent owned ancestry with bounded charged membership checks; do not call a finite leaf counter a bound on arbitrary uncharged ancestry copying.
6. Prove closure on ordinary native stacks and wasm: deepest accepted per-domain boundaries,42-node iterative spine, mixed self/mutual cycles, long acyclic mixed source chain, repeated DAG siblings with all contributions, fanout exhaustion, source/foreign-domain restoration, cancellation/unwind and iterative destruction. Refusals remain typed and cannot publish partial success. Only measured actual differential acceptance can promote the candidate to a closed preservation finding.

Ownership: retained_walk.rs and retained_entries.rs own typed ancestry/budget; existing inner.rs/inner_ready.rs plus inner_mapping/inner_type_map/inner_boolean/inner_product_adapter/inner_cancel own the common trampoline; mapping Path and Boolean OperandPath retain per-domain rules. Processing continues to own runtime issuance, tickets/ledger and final-product coverage, with no runtime receipts or SDK dependency moved into geometry. This is a conditional implementation design, not an instruction to rewrite those owners before an actual supported boundary is established.
