# Retained common-program continuation: required source changes

This remains an **incomplete migration**, following assembly of the inner program
and browser dependencies on parent `53dafdcf7f`. A consuming construction checkpoint
now connects logical retained values in the common product program to a private
processing transaction and sealed native construction receipts. Its behavioral
fixtures are **unrun**: syntax checks are not compilation or execution evidence.
Exact Rust remains the permanent default; final-net publication is unavailable.
The explicit source-only native/browser consumers retain their existing contracts.

The checkpoint selects `GeometryProgram::retained_parts` through the same reached
`ProductProgram`/Items admissions. Original extrusion and swept-disk source is
captured before sampled constructor lowering. `ItemResult` carries an explicit
mesh-or-logical-value variant; the common product control accumulates logical
values and continues to the next reached item only after accepting the original
reply. Repeated source ids produce distinct common child-program slots. Exact
mesh caches cannot discharge those values.

`element/session_retained.rs` selects that contract on the actual `ProductState`.
It captures the original outer/common request, engine-produced reply, strong Arc
ticket, stage, actual context and owner stamp, original source operation and f64
frames, and independently captured native runtime cancellation. Execution holds
only source lifecycle authority outside the dormant product. Acceptance checks
all captured identity and sealed receipt fields before taking the reply, reserves
ledger capacity, accepts the same reply and retains the actual sealed object in
the private ledger. Ordinary `ProductState::execute`/`accept`/mesh publication
cannot consume this contract.

This is **not** the complete requested retained implementation. Styled/type-map
contexts, affine occurrence semantics, common Boolean/group/opening operations
and their owned operands, browser transaction acceptance, managed native object
release, complete resource accounting and appearance closure remain required.
Unsupported reached source families refuse this selected contract without exact
retry. A completed traversal still carries opening, layer, appearance and
persistent-face requirements; it provides no final-product execution or coverage
authority. Only accepted late placement clears the placement requirement. See the
[checkpoint evidence](evidence/geometry-platform-retained-program-continuation/common-construction-checkpoint/README.md).

## P1 merged occurrence and placement source checkpoint

The common `MappingControl`/`MergedWalk` now has contract-disjoint mesh and
retained accumulators through child completion, append, finish, source cache
publication and placement. It keeps the existing frame stack, path guard and
source action order. The exact cache and its warm-hit timing remain separate.
The retained cache belongs to one product, binds its first router/decoder
execution identities and source revision, and rejects changed selected-cache
provenance. Templates contain immutable logical definition references in source
space, published before occurrence placement. They contain no SDK object.
Uncached repeated leaves remain separate definitions; cached DAG edges remain
separate occurrences. Resource admission charges emitted occurrences, retained
backing, cache copies and repeated search/append work.

`LogicalRetainedDefinition`, `LogicalRetainedSlot` and the original pending ticket
are different identities. Ordered `RetainedPlacement` records carry exact input
and output slots, source-map/product IDs and column-major metre matrices.
`world_from_evaluation()` composes each mapping after file-unit scaling of the
constructor's evaluation-to-source frame, then reached product placement. It
retains f64 survey translations without claiming mesh byte identity or folding
RTC into the analytic placement. Current proper-rigid checks do not implement
reflection, nonuniform scale or singular/nonfinite mapping semantics.

Retained values now use `ProductResources` and `ProductCompletion`, including the
existing late `ProductPlacementRequest`, source errors and world-frame admission.
Only accepted completion clears `ProductPlacement`. Processing keeps one original
sealed construction receipt per definition and validates all occurrence references
against that ledger, including runtime liveness. Source-free common operations
execute under their original request/resource context; physical affine baking
needs a separate immutable expected operation and sealed runtime receipt.

This is an incremental implementation, not complete P1 coverage or qualification.
Styled `SubmeshWalk`/type-map consumers, affine display/baking, native managed
object release, browser common transactions and behavioral execution are still
required. Existing native common wrappers retire the worker on drop; keeping
one wrapper per definition in a scoped ledger does not prove independent release.
Opening/layer/appearance/persistent-face requirements remain unresolved, and no
final-net API is provided. The source fixtures add nested millimetre/solid-position/
map-origin/product survey frames, a 256-edge diamond, cache-contract separation,
changed source-cache provenance, late placement errors, resource stops and actual
native mapped receipt cases. Their presence is not an execution receipt.

The following obstruction/design sections describe the broader migration and
must not be read as claiming that every accumulation family has been completed.

## Concrete obstruction in the assembled source

`element/session_inner.rs::PendingGeometryAttempt` now retains the actual
`GeometryProgram` across every reached request. However, its `finish` methods
still consume meshes on the default contract. `ItemResult` and common product
accumulation now additionally carry logical construction values on the explicit
contract. Boolean `Value`, styled/type-map mapping, layers and opening host
parts remain mesh values: they still need consuming retained continuations. `inner_ready.rs` now
admits original-source construction operations through nested common replies;
this admission alone makes no remote-execution claim.

The authored plan in `authored_geometry/planning.rs` is a partial analytic view:
it unconditionally records `RepresentationCoverageUnverified` and records
`EnclosingBoolean`/`ExternalOpening` requirements without lowering those
operations. Its family-local source ordinal cannot identify an occurrence in the
common program. `BoundAuthoredPlan` authenticates that view against the actual
decoder identity, but does not manufacture a missing common request or stage.
Its weak cache must stay keyed by `decoder.execution_identity()`.

Native `worker_dependencies.rs` already provides sealed
`RetainedDependencyResult`, immutable `RetainedOperationIdentity`, actual operand
handles and f64 frames. Browser `BrowserRealization` seals a source construction;
`BrowserWorker::new_retained_execution` now selects independent browser object
leases and exposes sealed `BrowserDependency::{Source,Result}` Boolean execution.
Its immutable identity records actual operand objects, operation and admitted
f64 frames; a result owns its own SDK object. This is an unqualified runtime
implementation checkpoint, not a consuming common-program contract. The default
`BrowserWorker::new` retains its source-only teardown boundary. Adding a ticket around `ModelBoundRetainedDocument::issue` would
still publish one authored source; it would not resume the reached product.

These are missing consuming contracts, not an asset-staging problem. A retained
mesh must not be injected into `ItemRecipe::Mesh` and treated as a retained
Boolean operand: that discards object identity and switches the enclosing
operation back to the exact mesh evaluator.

## Geometry-owned plan entry and values

Extend the existing entry constructors in `inner_entries.rs` with an explicit
contract-bearing entry. Existing constructors continue to select their exact
contract. The retained entry uses the same `ProductProgram` representation and
Items admissions and the same occurrence order. It never starts from a partial
`AuthoredGeometryPlan` or enumerates supported solids as substitute products.
No new STEP IDs or loader are involved. The independently owned imported entry
needs the same source-neutral contract in its own continuation work.

The geometry-side change must add these concepts together, not merely a new
`ProgramStage` variant:

1. A program-issued logical value slot (opaque program identity + monotonic
   occurrence identity), distinct from a runtime handle. Repeated mapped DAG
   occurrences retain their separate frames and share only qualified definitions.
2. A value variant carrying that slot and admitted f64 local/source/world frame
   lineage. Exact values continue to carry meshes. Every accumulation boundary
   must understand the selected value contract; a retained slot is never an
   empty mesh.
3. Immutable reached plan operations for construction, proper rigid occurrence,
   Boolean/group operands and ordered host-opening cuts. Preserve the original
   operator, operand order, short-circuit rules, source diagnostics and admission
   order. Source capture owns the original analytic recipe, not sampled mesh
   parameters renamed as analytic input.
4. Explicit unsupported requirements for source families, non-rigid transforms,
   clipping/half-space recipes, layer slicing, textures or appearance contracts
   that have no retained implementation. Propagate refusal through the selected
   retained contract; do not enter the exact retry/fallback ladder.
5. Contract-aware mapping/cache keys and cleanup. An exact mesh cache hit cannot
   discharge a retained operation. Program logical slots do not own SDK resources;
   the processing ledger owns their sealed realizations and actual lifetimes.

In particular, changing only `ItemResult` is insufficient. The consuming edits
span `inner_{product,product_adapter,mapping,type_map,layers,voids,opening}.rs`,
`product_control/{completion.rs,completion/placement.rs}`, Boolean
`{state,protocol,operand,batch,step,work,transitions}.rs` and their source/ready
adapters. Appearance remains late, and its explicit provenance requirements
must be met or refused. Current source-only flat display permission supplies no
IFC appearance or final-product coverage authority.

The geometry crate continues to own plans and control, with no dependency on
`geometry-runtime`. It never accepts a runtime handle number, mutable
`RetainedCompletion` or caller assertion that a remote operation succeeded.

## Processing-held pending transaction

Add `element/session_retained.rs` and target-specific execution modules beside
`session_inner.rs`. These are private processing modules. An explicit retained
execution owner selects them at creation; ordinary `produce_element_meshes*`
keeps its existing exact contract. Do not make failed exact work select retained
execution or failed retained work select exact execution.

A pending transaction must hold all of the following actual values:

- the original outer `WorkRequest`, original common `ProgramRequest`, and
  program-issued logical operation/continuation; no reconstructed ticket;
- a fresh strong `Arc<()>` bound to the issued work and a private pending stage
  distinguishing issued, executing, delivered and accepted;
- the captured `Arc<OwnedMeshProductionContext>`, its context identity and source
  lifecycle; the actual `ProductOwner` reservation stays owned by `ProductState`
  with its exact validated `OwnerStamp` captured in the pending transaction;
- an immutable expected operation (construction or exact Boolean discriminant),
  ordered operand slots, actual sealed operand realizations/handles, and the
  admitted f64 frames, including the selected result frame;
- the actual runtime incarnation/object owner and captured cancellation
  capability, resource admission, diagnostic state and target qualification;
- the engine-produced reply/continuation which will resume the **same** pending
  common request after runtime validation. No public method constructs a
  successful runtime receipt or a replacement common reply from supplied buffers.

One viable handoff keeps the common reply representing reached plan admission
inside this private pending transaction. It cannot be accepted through ordinary
exact `ProductState::accept`. The geometry continuation refers only to its own
logical output slot. After a sealed runtime result is validated and installed
under that slot, processing accepts that original reply and resumes the existing
control. This avoids introducing a public raw-buffer completion constructor into
geometry. A logical slot/admission reply alone proves no runtime execution;
only processing's private checked ledger can discharge it or publish output.

Source/extension admissions remain lexical under `ProductOwner::work`. Before
awaiting a browser operation, end the synchronous owner-work scope and restore
TLS, triangle-order and borrowed guards. Keep the actual lease reservation,
source/context identity, pending ticket and owned diagnostics dormant. Revalidate
that same reservation on resume; do not re-admit a new owner for the pending
request. Cancellation uses the captured independent browser cancellation
capability, even while its worker is borrowed by an async operation.

## Validate before linear consumption

Both target acceptors must inspect the intact pending transaction and receipt
before taking either. The order is:

1. Match the private Arc ticket, exact outer/common request and pending stage.
   Reject foreign input intact without retiring its foreign runtime.
2. Validate the captured context/source lifecycle and actual decoder/router
   `ProductOwner`. Reinstall only that owner's lexical resources and diagnostics.
3. Validate the sealed target receipt's live incarnation **and actual object**.
   Native dependency results must match `operation_identity()` against the stored
   operator, ordered operand handles and admitted f64 frames. A source result
   must match its original retained request/definition/revision and source frame.
   Compare browser equivalent identities from its sealed driver result, never
   from caller-supplied integers or mesh buffers.
4. Check contract-specific capability/qualification, resource and terminal state,
   immutable frame/lineage and result-slot eligibility. Prepare ledger capacity
   before changing either continuation or pending state.
5. Install the sealed result in the processing ledger, accept the original
   engine-produced plan reply, and clear the private pending transaction once.
   Retain input realizations for every dependent operation/occurrence still
   referencing them. Rejection returns the original receipt and keeps the pending
   state available; own-source expiry can retire its captured domain.
6. Only a completed common product with every reached slot discharged may enter
   canonical late presentation/assembly and final publication. A leaf receipt
   never clears representation, Boolean, opening or appearance requirements.

Native execution can consume the existing `RetainedDependency` API, but must
capture expected handles/frames at issuance, not copy the received identity as
its own expectation. Browser work first needs a sealed dependency result with
private construction in the imported driver, actual object leases, immutable
operation identity and symmetric copy/transform/Boolean semantics. Existing
source `BrowserRealization` is not that result. Neither target gains qualification
from the other's receipt or from JavaScript transport tests.

## Residual implementation and required evidence

The construction value/entry and native processing transaction are now source
implementations with behavioral fixtures, not qualified execution evidence. The
remaining geometry accumulation families and browser consuming transaction are
still unimplemented. The browser dependency-result prerequisite has protocol
fixtures and unrun actual browser tests; it has no SDK/common-product qualification.
The source-only native/browser consumers remain usable only under their existing
explicit contract. This document does not advertise new production APIs.

The construction checkpoint supplies a real-SDK fixture that issues a reached
construction, executes its original analytic recipe, accepts the sealed receipt
and resumes the original common request through product accumulation. It is
unrun under the current capacity restriction. Next qualify that fixture, then
qualify the merged mapped checkpoint and connect styled/type-map occurrences
and real Boolean/opening dependencies using actual sealed operands; preserve
explicit refusals throughout.
Final-net coverage remains withheld until representation/layer/appearance closure
is established across all reached branches.

Required behavior tests include foreign/expired source and owner rejection,
wrong stage/operator/operand/frame, cancellation between issue and execute and
during browser await, duplicate accept, intact rejection, dependent object
release and repeated mapped occurrences. Target numerical witnesses, workspace
and optimized Boolean regression, all-target Clippy, canonical WASM contracts,
root TS consumers, Python, real-scene identity/oracles and whole-pool performance
remain separate exact-source qualification. No heavy validation is authorized
under the current capacity restriction.

## P1 styled and type-map source checkpoint

The explicit common entries `GeometryProgram::retained_submeshes` and
`retained_type_map_id` now use the existing `MappingControl`/`SubmeshWalk` and
`TypeMapControl`. `Range`, `Append`, `MergeShared` and `FinishShared` carry
contract-disjoint values; no second traversal or exact-mesh retry is involved.
`finish_retained_type_map` accepts the already planned type-product id, geometry
class and fallback colour and returns a logical plan with remaining obligations.
Processing uses its existing `PendingGeometryAttempt` and `plan_type_geometry`
selection: a map referenced by products does not draw again directly, instanced
library geometry retains the viewer/export distinction, and each selected direct
map executes once. Several maps accumulate ordered values in the same execution.

Styled source order remains source, representation, transform, eligibility,
template, claim and whole Items. Retained template markers and source-local
values have their own contract-qualified cache namespace, authenticated against
router/decoder configuration and retained source revision. Mesh caches and exact
materialized-source markers do not authenticate retained hits. Template output
captures definition references before mapping placement. Placeholder recovery
uses the same shared child controls; each instance receives its own occurrence
slot and ordered placement history. Repeated uncached children remain separate
constructions. Textured and indexed-palette sources retain the canonical
exclusion from placeholders. Failed provisional retained template markers roll
back; completed independent source entries survive a later refusal.

`LogicalRetainedValue::presentation()` carries ordered geometry/style/map
bindings, template/placeholder roles and pending indexed-palette/texture inputs.
Texture coordinate/index arrays are owned snapshots of the reached index entry;
embedded pixels remain immutable shared backing. The processing execution also
owns the immutable source/context containing actual style, palette and material
indices. Those inputs are provenance and outstanding work, not evaluated colour,
material, normals or UV output. Type-product bindings retain their class and
fallback colour. Material resolution, palette splitting, persistent face lineage,
UV attachment and final display assembly still require canonical presentation.
No logical placeholder is a fabricated mesh, net solid or runtime receipt.

The new synthetic STEP fixture has actual repeated mapped triangles, a two-colour
indexed palette, embedded RGBA pixels and UV indices. Exact geometry and processing
fixtures assert nonempty UV/pixel and palette channels. They do not qualify the
retained tessellated-family constructor, which still refuses explicitly. Other
fixtures cover real retained extrusion DAGs, distinct styles/frames, template and
placeholder timing, type-map late origin, owner/configuration expiry and typed
resource stops. These source additions remain uncompiled and unexecuted until a
coordinated fleet run. They do not inherit the parent's earlier baseline result.

Remaining gates include affine integration and target qualification, exact
per-stage display/frame fidelity, native object lifetime integration, browser
common transactions, retained family completion, openings/layers and final
appearance/UV/material assembly. The exact kernel remains permanent and default.
