### IDS-008b: false positives on conforming corpus files (added mid-session)

   audit now resolves `IFCAIRTERMINAL` & co. through `rowForAlias` to the IFC2X3
   type entity.

   classifies `IfcResourceObjectSelect` members through

### What changed in the writer (IDS-001/002/003/012/014)

- `@ifc-lite/ids` exports `writeIdsXml(doc, fmt?)` and `IdsXmlFormat`;
  `@ifc-lite/rules` no longer exports it. The rules export had never been
  released (it lived in a pending changeset), so the move needs no shim; the
  pending rules changeset was rewritten and a new ids changeset added.
- Files: `writer/xml-lines.ts` (escaping, line buffer), `writer/constraint.ts`
  (simple value or one `xs:restriction` with the primary family and its `and`
  siblings), `writer/index.ts` (document).
- Refused, with a reason: unparseable bounds, two patterns or two
  enumerations in one conjunction (XSD ORs them), siblings with different
  bases, nested conjunctions, a bounds restriction without facets,
  non-integer counts, non-finite bounds, a voids-only or fills-only partOf.
- Written now that weren't before: every `info` field; `IFC4X3` as the XSD
  token `IFC4X3_ADD2`; bounds on `xs:decimal`/integer bases without exponent.
- Parser fix: `parseIDS` recognises the upper-case `ids.xsd` relation tokens
  and no longer echoes them as `rawRelation`.

### Gotchas and lessons

- The parser's image is the round-trip space. `parseRestriction` always
  orders families pattern → enumeration → bounds and copies one `base` to all;
  `IFC4X3_ADD2` reads as `IFC4X3`; `info` text is trimmed. The property test
  generates only parser-shaped documents and says so in its header. A
  document with families in another order still writes valid XML; it reads
  back reordered (matching is order-insensitive).
- The writer used to write `IFC4X3`, which the official XSD rejects (only
  `IFC4X3_ADD2` exists); our own XSD audit accepts both, so nothing noticed.
- `checkBounds` (coherence) and the requirement-emptiness check ignored
  `totalDigits`/`fractionDigits`, so a digits-only restriction was reported
  as empty. Fixed in IDS-010.
- `attribute/invalid-value_checks_always_fail_for_lists` is detected, but
  because its value `Foobar` is not an `xs:double`; the generated attribute
  tables carry no list flag, so `Coordinates = 1.0` would still pass the
  audit. Next step: emit a list/aggregate flag in
  `packages/data/scripts/generate-ifc-schema.ts` (the upstream
  `SchemaInfo.Attributes.g.cs` has the information) and flag value checks on
  aggregate attributes.
- IFC2X3 occurrences (IfcWall) have no PredefinedType; IDS reads it from the
  type object. The IDS-008 rule therefore looks up `<Entity>Type` and skips
  generic occurrences from the mapping table; only entities with neither
  (IFC2X3 IfcInventory) are flagged.
- Worktree tooling: shell commands with heredocs, loops or variables are
  refused by the sandbox in this environment; use the Edit tool or small
  script files.
- Viewer tests that import wasm cannot run here (no Rust toolchain and the
  published wasm lacks newer exports); viewer `tsc --noEmit` passes.

### IDS-013 (CI oracle against the official audit tool): design note only

- Job `ids-oracle.yml`, path-gated on `packages/ids/**`, plus `workflow_dispatch`.
- Steps: set up .NET 8; `dotnet tool install --global ids-tool.CommandLine`
  (pin the version); build `@ifc-lite/ids`; a Node script writes, for every
  corpus pass/fail case and every property-test seed's first N documents,
  `writeIdsXml(parseIDS(x), { canonical: true })` into `out/`; run
  `ids-tool audit out/*.ids --json`; a second Node script runs
  `auditIDSDocument` on the same files and diffs verdicts (valid/invalid per
  file, and error codes mapped to upstream report numbers where a mapping exists).
- Output: a markdown table of disagreements uploaded as an artifact and
  posted to the job summary. Fail the job only on NEW disagreements against a
  committed triage file (`docs/architecture/ids-studio/oracle-triage.md`)
  that classifies each known one as ours / theirs / spec ambiguity (the XSD
  parser issues IDS #422/#423 are known "theirs").
- Also run the tool on the 27 `invalid-` corpus files to confirm it rejects
  them (sanity for the tool version).
