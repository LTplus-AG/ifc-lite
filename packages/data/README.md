# @ifc-lite/data

Columnar data structures for IFClite. TypedArray-backed storage for entities, properties, quantities, and relationships — the layout that lets `@ifc-lite/parser` hold a 200 MB IFC file in ~30 MB of RAM and lets `@ifc-lite/query` filter it in milliseconds.

## Installation

```bash
npm install @ifc-lite/data
```

## When to use this directly

Most users get these structures for free as the output of `@ifc-lite/parser`'s `parseColumnar()`. Use this package directly when you're:

- Building a custom data source (e.g. server-side parquet → IFClite tables)
- Writing a tool that consumes the columnar format outside the parser pipeline
- Looking up EPSG codes (the geo-reference index is shipped here)

## Build an entity table

```typescript
import { EntityTableBuilder, StringTable } from '@ifc-lite/data';

const strings = new StringTable();
const entities = new EntityTableBuilder(1, strings);

// add(expressId, type, globalId, name, description, objectType)
entities.add(42, 'IFCWALL', '1abc2def3...', 'Wall A', '', '');

const table = entities.build();

console.log(table.count);                    // 1
console.log(strings.get(table.name[0]));     // 'Wall A'
console.log(table.getTypeName(42));          // 'IfcWall'
```

## Relationship graph

Edges are stored CSR-style (compressed sparse row) — fast to traverse, compact in memory.

```typescript
import { RelationshipGraphBuilder, RelationshipType } from '@ifc-lite/data';

const builder = new RelationshipGraphBuilder();

// Storey 100 contains walls 42, 43, 44 (last arg = the IfcRel* express id)
builder.addEdge(100, 42, RelationshipType.ContainsElements, 200);
builder.addEdge(100, 43, RelationshipType.ContainsElements, 200);
builder.addEdge(100, 44, RelationshipType.ContainsElements, 200);

const graph = builder.build();

const contained = graph.getRelated(100, RelationshipType.ContainsElements, 'forward');
console.log(contained); // [42, 43, 44]
```

## EPSG lookup

The full EPSG database ships as a pre-built index — geo-referenced models can resolve coordinate systems offline at runtime.

```typescript
import { lookupEpsgByCode, searchEpsgIndex } from '@ifc-lite/data';

const lv95 = await lookupEpsgByCode(2056);
// { code: '2056', name: 'CH1903+ / LV95', kind: 'projected', ... }

const matches = await searchEpsgIndex('web mercator');
// → top text-search results; ordered by relevance
console.log(matches.map(m => `${m.code} ${m.name}`));
```

The index is generated at build time and committed to the repo, so normal builds stay offline. Refresh it with `pnpm generate:epsg-index`.

### Area of use and unit

A separate, lazily loaded sidecar (about 59 KB gzipped, generated by `pnpm generate:epsg-extents` from the EPSG registry) carries each CRS's area of use, native units and compound components:

```typescript
import { getEpsgAreaOfUse, getEpsgUnits, isLonLatInEpsgAreaOfUse, createEpsgCrsCatalog } from '@ifc-lite/data';

await getEpsgAreaOfUse(2056); // { west: 5.95, south: 45.81, east: 10.5, north: 47.81, crossesAntimeridian: false }
await getEpsgUnits(2227);     // { horizontal: { name: 'US survey foot', metres: 0.3048006096 } }
await isLonLatInEpsgAreaOfUse(2056, 2.3, 48.85, 0.5); // false (Paris); undefined when no area is known

const catalog = await createEpsgCrsCatalog(); // sync lookup(code) / resolveName(name)
catalog.lookup(3460)?.areaOfUse?.contains(-179, -16.5); // true: Fiji, east of the date line
catalog.resolveName('CH1903+ / LV95'); // 2056
```

- **Antimeridian.** A box with `west > east` crosses the date line and is published that way, with `crossesAntimeridian: true` (92 CRSs, for example 3460 Fiji). Test membership with `areaOfUse.contains(lon, lat, marginDegrees?)` or `isLonLatInAreaOfUse`; a plain `lon >= west && lon <= east` is wrong for those boxes.
- **Several usages.** `catalog.lookup(code).areaOfUse` is the bounding hull of every current usage (15 CRSs have more than one; none of them crosses the date line). `getEpsgAreasOfUse` returns every box and `isLonLatInEpsgAreaOfUse` tests the exact union.
- **Units.** `unitScale` is metres per unit of the horizontal axes and is absent for angular CRSs, for vertical-only CRSs and for the `(bin)` unit of four Derived/Engineering CRSs (no metre factor). `verticalUnitScale` is the vertical axis; `getEpsgUnits` returns `{ horizontal?, vertical? }` with unit names.
- **Names.** `resolveName` accepts an exact CRS name (case- and whitespace-insensitive), a multi-word EPSG alias, `EPSG:2056`, `EPSG::2056`, `EPSG 2056`, `urn:ogc:def:crs:EPSG::2056` and a bare code; unknown or ambiguous names give `undefined`. One-word aliases (`Israel`, `Madrid`, `LV95`) are not resolved, because they often name a place or a datum rather than one CRS, and neither are viewer-style nicknames (`wgs84`, `rd new`, `lambert-93`).
- **Helper limits.** `|lat| > 90` and non-finite input are outside every box; a negative margin throws a `RangeError`.

#### Dataset versions

The sidecar was generated from EPSG dataset **13.106** (`loadEpsgExtentsDatasetVersion()`, constant `EPSG_EXTENTS_DATASET_VERSION`); the main index above is dataset **12.054** (`loadEpsgIndexDatasetVersion()`). Only the list of codes is taken from the index. The two can disagree: a 300-code sample showed extents redefined (20001) and names changed (10986, 10164, 9508, 20001) between the versions. Bringing the main index up to 13.106 is a separate change.

The extents data is provided "AS IS" under those terms, without warranty of any kind. It is **not** the EPSG Dataset but a derived subset. The generator applies exactly these transformations to registry data:

1. Only the codes of the bundled index are kept, and only area-of-use bounding boxes, the native axis unit and the component codes of compound CRSs. No CRS definition, datum, projection or parameter is included.
2. Usages the registry marks deprecated are dropped; every current usage's extent is kept and identical boxes are stored once.
3. Bounding-box values are rounded to 6 decimal places.
4. Metres per unit is `FactorB / FactorC` rounded to 10 decimal places, only for length units whose target is the metre; the unit is the first axis of the CRS's coordinate system and the suffix ` (supplier to define representation)` is removed from unit names.
5. A compound CRS takes its horizontal component's unit.
6. Rows are stored as JSON arrays in shared tables (units, boxes).

The generator exits non-zero and writes nothing if any code of the index has no registry row, unless the code is listed with a reason in `scripts/epsg-extents-allowlist.json`.
