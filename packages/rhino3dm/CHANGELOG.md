# @ifc-lite/rhino3dm

## 0.2.0

### Minor Changes

- [#9880](https://github.com/LTplus-AG/ifc-lite/pull/9880) [`1cf1510`](https://github.com/LTplus-AG/ifc-lite/commit/1cf15109f8085a0b807989f4aaae5041233769cd) Thanks [@louistrue](https://github.com/louistrue)! - Add `readRhino3dm`, which reads a Rhino `.3dm` into plain `RhinoImport` data: Z-up metres, typed arrays, double-precision origins, layers, colours, Attribute User Text as property sets, and IFC identity (`IFC::GlobalId`, `IFC::Class`) for files ifc-lite exported. Blocks come back as definitions plus instance transforms (or baked with `bakeInstances`), and point clouds, curves and text dots as data. Failures throw `RhinoReadError` with a `code`.

- [#9883](https://github.com/LTplus-AG/ifc-lite/pull/9883) [`942d565`](https://github.com/LTplus-AG/ifc-lite/commit/942d56555fdaf0c0572708516f202df76a0fb6b2) Thanks [@louistrue](https://github.com/louistrue)! - Rhino .3dm export stamps the layers that stand for the project and the spatial structure (site, building, storey) with `IFC::GlobalId` and `IFC::Class` layer user text, and storeys with `IFC::Elevation` in metres, so a reader can rebuild the IFC spatial tree from the layer table. `RhinoLayer` in the scene manifest gains a required `userStrings` field, which `writeRhino3dm` writes with `Layer.setUserString`.

- [#10102](https://github.com/LTplus-AG/ifc-lite/pull/10102) [`d137af4`](https://github.com/LTplus-AG/ifc-lite/commit/d137af41a4fc4e623a50e365fa89ceb0cac0235b) Thanks [@louistrue](https://github.com/louistrue)! - `readRhino3dm` charges a mesh's vertices to `maxTriangles`: a mesh costs its triangles or a third of a triangle per vertex, whichever is more. Curves and point clouds were already charged by vertex; the budget is now counted in whole thirds of a triangle, so parts that fill it exactly are no longer refused by float rounding (three 5-point curves at `maxTriangles: 5` drew two). A mesh with few triangles over a large vertex array was nearly free before. Meshes whose triangles use every vertex cost the same as before. Each mesh, instance, point cloud, curve and text dot record now carries `hidden`, the flag of the object that drew it, so an entity merged from a group of visible and hidden parts keeps which part Rhino hides ([#10070](https://github.com/LTplus-AG/ifc-lite/issues/10070)).

- [#9416](https://github.com/LTplus-AG/ifc-lite/pull/9416) [`3fd7a97`](https://github.com/LTplus-AG/ifc-lite/commit/3fd7a971ee651fffec45421bac3bcf1106d231cf) Thanks [@louistrue](https://github.com/louistrue)! - Add a lazy RhinoScene v1 to Rhino 7/8 3dm adapter with validated binary references, double precision meshes, layers, materials, groups, block instances and IFC user text.

- [#9977](https://github.com/LTplus-AG/ifc-lite/pull/9977) [`14de48e`](https://github.com/LTplus-AG/ifc-lite/commit/14de48e75922802a99fed061e475e6848d1359b5) Thanks [@louistrue](https://github.com/louistrue)! - `@ifc-lite/rhino3dm` exports `MAX_3DM_BYTES` and `tooLarge3dmMessage`, from a module that imports nothing, so a caller can check the size cap on the main thread without loading rhino3dm. The viewer uses them for its pre-copy check instead of a copy of the number and sentence. File sizes in both `too-large` messages now round up: a file just over the cap read "This file is 400 MB; the reader handles up to 400 MB", and now reads 401 MB.

### Patch Changes

- [#9865](https://github.com/LTplus-AG/ifc-lite/pull/9865) [`a6a6331`](https://github.com/LTplus-AG/ifc-lite/commit/a6a63314fa4c5da2696e394c727e57dee461ba66) Thanks [@louistrue](https://github.com/louistrue)! - The IFC class lookups read the entity tables through their getters (`getEntitiesIfc4x3()`, `getEntitiesIfc4Express()`, `getEntitiesIfc2x3()`), so a bundle that includes the Rhino importer no longer keeps the eager table constants on its startup path. Same lookups, same results.

- [#10032](https://github.com/LTplus-AG/ifc-lite/pull/10032) [`71b590a`](https://github.com/LTplus-AG/ifc-lite/commit/71b590aaed61180398e55155663215164cbde1e3) Thanks [@louistrue](https://github.com/louistrue)! - A Rhino block member that inherits its material from the instance placing it now resolves its colour and transparency from that material ([#9987](https://github.com/LTplus-AG/ifc-lite/issues/9987)). Two rules were wrong. A member with `ColorFromMaterial` plus `MaterialFromParent` took the instance's object colour; it now takes the diffuse colour of the instance's material, so a red instance carrying a blue material draws such a member blue. And an inherited material's transparency was skipped, on the theory that the instance's colour already carried it; it does not, so a member with its own colour and an inherited glass material now comes back faded instead of opaque.
  
  `ON_3dmObjectAttributes::ApplyParentalControl` in openNURBS, the function Rhino itself uses, settles both: it overwrites a "by parent" material with the instance's and leaves the colour source alone, which leaves the member indistinguishable from one that owned that material. It was run over all 144 combinations of a member's and an instance's two sources, and the resolution table with its citations is in `docs/architecture/rhino-3dm-import.md`.
  
  Members whose colour or transparency comes from the instance's material are now baked per placement, because one instance record carries one colour. A member that only inherits the material stays in the shared definition when no material a block instance hands down is transparent, since nothing can then fade it: without that gate, 5,000 placements of one 3,200-triangle member came back as 5,000 mesh records and 375 MB of geometry, all the same colour, where one definition holds 0.08 MB. The gate is measured over what the instances resolve to, not over the material table, so a transparent material the file stores but nothing uses does not bake anything. Both the instanced and the baked mode draw the same colours and the same triangle count. The neighbouring rules were already right and are now covered: `ColorFromLayer` on a member reads the member's own layer and never the instance's, `ColorFromParent` takes the instance's resolved colour, both sources fall back to the object's own layer at top level, and nesting resolves against the direct parent.

- [#10075](https://github.com/LTplus-AG/ifc-lite/pull/10075) [`51c2a82`](https://github.com/LTplus-AG/ifc-lite/commit/51c2a823c7aab6ce8d8be44257f09c6f0d6f7212) Thanks [@louistrue](https://github.com/louistrue)! - Six robustness fixes in the Rhino `.3dm` reader and writer ([#10021](https://github.com/LTplus-AG/ifc-lite/issues/10021)).
  
  - What the triangle budget draws no longer depends on `bakeInstances`. It was charged per block with `bakeInstances: false` and per mesh with `true`, so a block of two 12-triangle boxes at `maxTriangles: 12` refused the file in one mode and returned one box in the other. A placement whose block reach keeps the f32 range is now admitted whole or left out whole in both modes; what a placement draws beside those meshes, and the meshes of a placement the reach refuses, are charged one part at a time, as before and the same either way.
  - `readRhino3dm` and `writeRhino3dm` reacquire the wasm module until it is the one still in use, through one helper that runs the parse or the write in the same step as its check. One recheck left a third read, waiting through two aborts in a row, parsing with a module that had just been discarded; the writer had no recheck at all.
  - The block walk checks the placement limit on every reference, skipped ones included, so it stops on the reference that spends the budget instead of walking to the end of the block it is in.
  - A composed transform no longer carries the rounding noise `IFC::WorldFromModel` is allowed in its last row: that noise grows with the translation it meets, and an identity frame holding 1e-17, composed with a placement a million metres out, refused every block instance under a frame that had been accepted.
  - Layer paths are built from the parent order the reader settles on, not from rhino3dm's `Layer.fullPath`, which follows `ParentId` with no visited set and does not return for a cyclic chain. Paths of well-formed files are unchanged.
  - A table row the binding does not hand out is reported as a damaged file instead of escaping as a `TypeError`.
