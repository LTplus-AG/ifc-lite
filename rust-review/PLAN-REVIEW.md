Reviewer: principal-engineer pass, read-only. Repo root for every `path:line` below is `/home/louistrue/.t3/worktrees/ifc-lite/t3code-b066fae6` at `main` @ `5bc1dae581`. ## Verdict

Not approvable as written. The WP decomposition and the wave order are mostly sound, and the plan is right to put crash/DoS fixes first and to insist on the R/X split. But the evidence model it rests on is wrong in two places that matter: the "three byte-identity oracles" (§1.2, §5.3, T3) do not exist in the form the plan assumes (the ifcopenshell "reference" is IfcOpenShell's output and cannot change with an ifc-lite PR; the `mesh_determinism` manifests pin one synthetic 6-mesh fixture that none of the B6 bugs touches), while the two oracles that actually catch geometry drift today (the 25 insta snapshots in `rust/geometry/tests/snapshots/` and `perf_probe --fingerprint`) are never named. The plan also omits a release-process cost that will hit almost every F/C PR: every `pub` removal in a published crate must be recorded in `rust-major-offset.json` and passes a `cargo-semver-checks` gate at release. Three architectural choices (D1 new math crate, D2 new model crate, C4 "one process API replacing the wasm entry") are the more expensive option when a module in an existing crate does the job, and each new crate costs a crates.io bootstrap plus edits to three workflow path filters. Several WPs bundle three or four defect classes (F2, C1, C2, C9, S6, B10) in a way that breaks "one defect class per issue", and the T2 verification wave is exactly the qualification machinery the maintainer's past campaigns stalled on. With the must-fix items below the plan is approvable; the critical path and most of the mapping survive.

## Must-fix (blocks approval)

### MF1. Replace the "three byte-identity oracles" with the oracles that exist (§1.2, §5.3, T3, G8)

## Decisions D1-D6, and missing decisions

**D1 (math home: new crate vs geometry module).** Disagree with the recommendation. Clash's vector/AABB/triangle math is Plato-generated from `tools/plato/clash_math.plato` as the single definition, byte-compatible with `packages/clash` (`rust/clash/src/generated/mod.rs`), and the crate is zero-dependency on purpose (`rust/clash/Cargo.toml` has an empty `[dependencies]`; `rust/geometry/Cargo.toml:141`). What clash would take from a shared crate is a constant (`2^-22`, EDGE-CLASH-8) and a 14-line `canonical`/box-normal helper (EDGE-CLASH-4, XCUT-19). That does not justify a published crate with the MF3 costs. Every other consumer of v3/mat4/Aabb3/frame (processing, export, wasm, server, landxml) already depends on geometry (XCUT-4's own fix says so). Recommendation: `ifc_lite_geometry::math::{v3, mat4, aabb, frame, tol}` now, each module under 400 lines. For the clash seam: geometry already dev-depends on clash (GEOM-33, `test.yml:1795`); either promote that to a normal dependency so `clash_contact_axes` consumes clash's Plato types, or keep the 14-line clone under a parity test. Core (`model_bounds.rs`, XCUT-8) stays out of scope for the math home; its `ModelBounds` is six fields. Revisit a crate only if a consumer that cannot depend on geometry appears.

**D2 (server depends on `ifc-lite-model`).** Disagree with the new crate; agree with deleting the server's fourth pipeline. Export's model code depends on processing and geometry (`rust/export/src/model.rs:18-20`), so the extracted crate would too, and the server already depends on both — the "bigger dependency graph" cost is nil, but so is the layering benefit. The SERVER-3 reviewer recommends `ifc_lite_processing::data_model`; processing already holds the third pipeline (`processor/properties.rs`, `quick_metadata.rs`) and is a dependency of server, export, python, wasm and ffi. Recommendation: `ifc_lite_processing::data_model` (typed pset/qset/material/classification/relationship/spatial rows), consumed by export's CSV/JSON/BOS writers and the server's Parquet writer; delete `apps/server/src/services/data_model/{properties,quantities,relationships,materials,classifications}.rs` and the two TS-fed generators (`scripts/generate-server-attr-indices.mjs`, `scripts/generate-server-relationship-slots.mjs`). F3c and F3a give it typed values and units. Extract to a crate later only if a consumer needs the model without geometry.

**D3 (fail-closed vs default-to-zero).** Agree. Two conditions: it is an X change with user-visible element loss, so it needs the real-model before/after and a refused-element counter surfaced in `ProcessingResult` (so the viewer can say "N elements refused", which is a viewer decision to name now); and it must follow reconcile-then-delete: one X PR makes every copy refuse (tests pin it), then the R PR collapses the copies. Do not combine the policy change with the consolidation.

**D4.** See MF4.

**D5 (TS twins in the same PR).** Agree. Add that the parity vectors are files under `rust/export/tests/fixtures/*.json` (12 today) and the TS packages, so the PR needs `pnpm changeset` for the TS package and, if the Rust signature changes, the offset entry from MF3.

**D6 (generated-code slimming in a major).** Half agree. A Rust major is routine here (offset 10, three bumps in one September week, `IfcType` already the subject of breaks #7 and #8 in `rust-major-offset.json`), so C10 is one more recorded break, not a special event. Do not couple it to F5: two large breaks in one release PR make both revert-hostile and hold C10 hostage to the slowest per-crate F5 lane. Land C10 when its prerequisites (C4, C6) are in, record its break, and let the next release carry it.

Missing decisions the maintainer must make:
- **D7 Rust crate publishing during the campaign.** Each release window with a public-API break costs one offset bump and a measured account. Options: (a) accept a Rust major roughly per release for the duration; (b) pause crate publishing (skip `release-crates.mjs`) until the foundations and migrations land, then publish once; (c) keep `pub` items alive as `#[deprecated]` shims until the end (contradicts supersede-means-delete and bloats every migration). Recommend (a); it is what the repo does today.
- **D8 Stop line and budget.** What ends the campaign if it does not reach §0: a PR count, a date, or a theme set (A-E and the S/B fixes done; C5-C13 and L optional). Without it the charter has no stopping point, which AGENTS.md "A sweep needs a charter" exists to prevent.
- **D9 Test-binary folding (XCUT-22, GEOM-8).** Folding 240 integration-test binaries is many PRs of pure churn with real risk of silently losing fixture-gated coverage. Recommend: fold only when a test file is touched for another reason; never as a sweep.
- **D10 Terrain CDT ownership.** Move `rust/geometry/src/{cdt.rs, cdt/, terrain_cdt.rs}` into landxml (XCUT-19, KERNEL-35), or record `wontfix` with the reason. It touches the published geometry API.
- **D11 NaN policy for sorts (S2).** Reject NaN at the boundary (fail-closed, consistent with D3) or order it (`total_cmp`, NaN last). `rust/AGENTS.md` forbids clippy's rewrites for exactly this ambiguity, so it needs a stated answer per sort.
- **D12 Browser API surface in scope?** C4/C10/EDGE-WASM-12/17/30 change `@ifc-lite/wasm`'s exported surface, which is an npm major that ripples to the viewer and SDK. Decide whether the campaign may ship wasm majors, or whether the browser keeps its entry points and only the Rust internals are shared.
