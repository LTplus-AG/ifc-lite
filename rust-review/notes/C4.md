### TL;DR

1. **One native entry point.** `pub fn process(content: &[u8], req: &ProcessingRequest, sink: &mut dyn ProcessingSink) -> ProcessingResult`.
   - `ProcessingRequest` is a `#[non_exhaustive]` value type with a builder. It absorbs `OpeningFilterMode`, `StreamingOptions`, the private `PassScope` and the id allow-list.
   - `ProcessingSink` has default no-op events: `on_bootstrap`, `on_frame`, `on_batch`, `on_color_update`, plus the optional `on_finishes`.
   - `process_geometry(content)` stays as the one convenience (287 uses).
   - The other **10 public entry points** become one-line delegates in C4-1, are `#[deprecated]` in C4-3, and are deleted in C10 (D6).
2. **The baked basis and finishes are sink events, not new `ProcessingResult` fields.** So C4 is **additive** for `ifc-lite-processing`. The one break #11 append is `PipelineDiagnostics` (browser refusal counters, X PR C4-10a).
3. **The browser keeps its JS entry points unchanged (D12).** The 7 batch/pre-pass `js_name`s and their `.d.ts` stay byte-identical. Behind them, the wasm crate keeps only wire decoding, the JS conversion and its session cache. Every decision comes from processing:
   - `scan::{ScanClass, ScanCollector}`, the one discovery table (with `ifc_lite_core::is_geometry_job` underneath);
   - `plan::TypeGeometryPlan`;
   - `element::{BatchRouterConfig, GeometryPass}`;
   - `style::resolve_element_color`.

   Native runs `GeometryPass` under rayon, one router per job. The browser runs it serially, one router per batch. There is one body and two schedulers.
4. **`ContentCaches`** replaces 15 hand-listed `Mutex<Option<…>>` slots on `IfcAPI`. It has two tiers:
   - **inputs:** source bytes and entity index;
   - **derived:** everything built from them.

   Every content install calls `reset_derived()`. `clearPrePassCache` calls `reset()`. Session settings and the diagnostics accumulator are not content-scoped.
5. **One new drift needs the maintainer.** On main, the native pipeline builds the #563 `MaterialLayerIndex` and attaches it to the auxiliary router, which meshes nothing (`processor/mod.rs:1069-1078`). The per-job routers (`jobs.rs` `process_entity_job`) never get it. So **server, export, FFI and Python never slice layered walls; the browser does** (`batch.rs` `!merge_layers()`). C4 keeps native unsliced by default and deletes the dead build as R. Turning native slicing on is a user-visible X (D66).
6. **About 22 PRs (13 R, 9 X).** They remove **5 of the 6 function-length rows** in scope, including the 1,166-line `process_geometry_streaming_filtered_with_options_and_ids` and the 589-line `produce_batch`, and **5 module-size rows**.

### 1. Native API

#### 1.1 `ProcessingRequest`

```rust
// rust/processing/src/processor/request.rs (new, MPL header)
#[non_exhaustive] #[derive(Debug, Clone)]
pub struct ProcessingRequest {
    pub opening_filter: OpeningFilterMode,              // kept enum, unchanged
    pub quality: TessellationQuality,
    pub batching: Batching,                             // { initial, throughput, fast_first: bool }
    pub features: Features,                             // { properties, presentation_layers, quick_metadata_bootstrap, finishes }
    pub retain_meshes: bool,                            // = StreamingOptions.retain_emitted_meshes
    pub instancing: bool,                               // = StreamingOptions.enable_instancing
    pub entity_ids: Option<Arc<HashSet<u32>>>,          // None vs Some(empty) contract kept (mod.rs:933-941)
    pub entity_index: Option<Arc<EntityIndex>>,
    pub cancel: Option<Arc<AtomicBool>>,
}
impl Default for ProcessingRequest   // == StreamingOptions::default() + OpeningFilterMode::Default (batches 50/50)
impl ProcessingRequest {
    pub fn full_pass() -> Self;       // batches usize::MAX: today's id_filter.rs `full_pass_options`
    pub fn opening_filter(self, m) -> Self; pub fn quality(self, q) -> Self; pub fn ids(self, ids) -> Self;
    pub fn index(self, i) -> Self; pub fn cancel(self, c) -> Self; pub fn batching(self, b) -> Self; …
    #[doc(hidden)] pub fn from_streaming(m: OpeningFilterMode, o: StreamingOptions) -> Self; // delegates only; C10 deletes
}
```

- **Not added:** no frame override (`FrameRequest`), router knobs (`skip_small_cuts`) or layer slicing. No native caller asks for them, and adding one would be new behaviour, not consolidation.
- **`entity_ids` becomes an owned `Arc`.** Today it is a borrowed `&HashSet` inside `PassScope`. Python wraps its set once, at O(n), which is negligible next to tessellation.

#### 1.2 `ProcessingSink`

```rust
pub trait ProcessingSink {
    fn on_bootstrap(&mut self, _b: &QuickMetadataBootstrap) {}          // mod.rs:1040, end of scan
    fn on_frame(&mut self, _f: &FrameEvent) {}                          // once, where publish_baked_basis runs today (mod.rs:1107)
    fn on_batch(&mut self, _m: &[MeshData], _processed: usize, _total: usize) {}  // mod.rs:1453
    fn on_color_update(&mut self, _u: &[(u32, [f32; 4])]) {}            // mod.rs:1481 (deferred styles)
    fn on_finishes(&mut self, _f: &ModelFinishes) {}                    // only with features.finishes (C4-13)
}
#[non_exhaustive] pub struct FrameEvent { pub frame: MeshFrame, pub baked_basis: Option<[f64; 16]> }
impl ProcessingSink for () {}
/// Adapter the delegates use: three closures → a sink. Deleted with the delegates in C10.
#[doc(hidden)] pub struct ClosureSink<B, C, Q> { … }
```

- **Ordering contract** (pinned by a test in C4-1): `on_bootstrap` ≤ 1, then `on_frame` = 1, then `on_batch`* interleaved with `on_color_update`*. `on_frame` fires **before** the first `on_batch` even when there are zero jobs, which is today's `OnceLock` semantics.
- **Refusal counters are not events.** `refused_input_elements` and `refused_prepass_records` stay in `ProcessingResult.stats`, where S6a puts them, so every consumer gets them without a sink. The C2 X5 `VoidPathStats` arrive the same way, through `stats.geometry_diagnostics`.

**Byte-identity of the delegates.** Each delegate builds the exact `StreamingOptions` + `PassScope` it builds today, converted by `from_streaming`. `process` runs today's body unchanged. The closures are monomorphised today and become one `&mut dyn` call per chunk (one per ~50 elements), not per element.

**Caller migration** (C4-2, production; C4-3, tests):
- **Server.** `streaming.rs` gets a `struct SseSink { tx, finishes, baked_basis: Option<[f64;16]>, started, batch_number, last_type, cancel }`. Its `on_frame` stores the basis that the batch arm reads today through `OnceLock::get`. The JSON and both parquet routes call `process(&c, &full_pass().opening_filter(m).quality(q), &mut ())`.
- **FFI:** `process(&c, &full_pass().opening_filter(mode), &mut ())`.
- **Python:** `.ids(ids.map(Arc::new))`. Build and test in-dir (`rust/python`, `tests/test_bindings.py`) per §1.3.
- **Export:** gltf ×6 and usd ×3 use `from_streaming` at first. Their own option literals become builder calls in the same PR.
- **wasm:** only `diagnose.rs` (`process_geometry`, unchanged). The batch path is not a `process` caller (§2).

### 2. Browser batch entry and shared internals

#### 2.1 What the browser keeps

These JS entry points stay as they are, with the same `.d.ts`:
- `buildPrePassOnce`, `buildPrePassStreaming[WithSourceFingerprint]`, `buildPrePassStreamingSharded[WithSourceFingerprint]` and the shard trio;
- `processGeometryBatch`, `processGeometryBatchInstanced`, `processGeometryBatchPartitioned`, `processGeometryBatch[Partitioned]FromSource`;
- `setEntityIndex`, `setSourceBytes`, the `set*` column installers, `clearPrePassCache`.

The "one pull-driven batch entry" is one Rust function, `IfcAPI::run_batch(&BatchWire, Source) -> BatchOutput`. The five `processGeometryBatch*` wrappers become ≤ 20-line adapters over it (EDGE-WASM-12):
- `BatchWire` is a Rust struct, not a `#[wasm_bindgen]` type, so there is no JS change. It is built from today's 16 positional arguments.
- `Source` is `Bytes(&[u8]) | Held`.

JS still pulls jobs from the pre-pass and calls batches. Nothing in C4 adds a push or stream API to wasm.

#### 2.3 Native pipeline phases (PROCESSING-8, PROCESSING-14, PROCESSING-21)

`processor/mod.rs` becomes the sequencer, about 150 lines:
`scan.rs` (`ScanOutput`) → `plan.rs` (`TypeGeometryPlan`, job synthesis) → `resolve.rs` (`ResolvedContext`: index install, `resolve_prepass`, unit scales, opening filter, id filter, frame) → `pass.rs` (chunk loop, `GeometryPass`, sink emission, cancel) → `finalize.rs` (instancing finalize, diagnostics, `ProcessingResult`).
- The quick-metadata tree build (`mod.rs:953-1045`) moves into `quick_metadata.rs`.
- The `cfg(wasm32)` metadata fork (`populate_entity_job_metadata`, `mod.rs:244`) becomes `decode_job_identity` + `resolve_job_appearance`. That is one body each, called under `par_iter_mut` on native and serially on wasm32.

Each new file stays under 400 lines.

### 3. `ContentCaches::reset()` semantics

```rust
// rust/wasm-bindings/src/api/content_caches.rs (new)
pub(crate) struct LazySlot<T>(Mutex<Option<Arc<T>>>);   // get_or_build(|| ..), set, take; poison-tolerant
pub(crate) struct ContentCaches {
    // inputs (installed by JS or by a pre-pass)
    pub entity_index: LazySlot<ColumnarEntityIndex>, pub source_bytes: LazySlot<Vec<u8>>,
    // derived (built from the inputs or installed by the pre-pass for them)
    pub item_dedup, mapped_item, parts_to_skip, material_layer_index, referenced_repmaps,
        instantiated_type_ids, mapped_instance_plan, texture_index, indexed_colour_maps,
        plane_angle, geometry_styles, style_finishes, pending_geometry_finishes: LazySlot<..>,
}
impl ContentCaches {
    /// Drop every derived slot. Exhaustive `let Self { .. } = self` destructure: a new
    /// slot that is not reset fails to compile (the EDGE-WASM-11 class).
    pub fn reset_derived(&self);
    /// Inputs and derived: end of load (`clearPrePassCache`).
    pub fn reset(&self);
}
```

### 6. Perf contract

1. **Native.** Run `scripts/perf/instructions.sh`, base vs branch, on AC20-FZK-Haus (CI `native-instructions`), ISSUE_129 (`--set large`) and duplex. Every phase must be ≤ base × 1.0005, with no trading between phases. The PR posts the table.
2. **Interleaved A/B.** `scripts/perf/probe.sh`, interleaved, must give a neutral verdict. The CI perf ratchet must be green, with no ceiling raised.
3. **Browser.** There is no Ir harness for wasm. Every W-lane PR runs the wasm batch over the corpus (`pnpm test:wasm-contract` fixtures plus AC20 and ISSUE_129 through `buildPrePassOnce` → `processGeometryBatch`), 5 interleaved runs. The median must be ≤ base + 1 %, and peak `getMemory` must be ≤ base.
4. **Rules that keep R PRs neutral:**
   - one `dyn` sink call per chunk, never per element;
   - `PassContext` passed by reference;
   - `ScanClass::classify` is a `match` on the first keyword bytes, no allocation, no `HashMap`;
   - `GeometryPass` is generic over the scheduler (monomorphised);
   - `LazySlot::get_or_build` takes the lock once on a hit, as today;
   - no new `Arc` clone per element.
5. **Perf-positive PRs** (7b, 11b, 13a, 14, 10a's dead-build removal) land only with a measured win:
   - ≥ 0.5 % `geometry`/`scan` Ir, or ≥ 2 % browser pre-pass wall time on a named fixture;
   - no other phase worse than +0.05 %.

   Otherwise they are closed, not merged.

### 11. The three most likely failure modes

1. **The browser-side refactors are invisible to the native fingerprint.**
   - C4-6b, 7b, 9, 10b and 11b change only `wasm-bindings`. `perf_probe --fingerprint` runs native code, so an R PR could drift the browser while passing (a)–(f).
   - *Mitigation:* evidence (h) is mandatory for these PRs: the wasm32 manifest, a non-skipping `test:wasm-contract`, and the C4-0 parity harness with an `EXPECTED_DIFF` table that only shrinks. The adversarial reviewer runs C4-0 at base and at head.
2. **Phase-split side-effect reordering (C4-4b).** The 1,166-line function interleaves:
   - sink emission;
   - deferred style replay (`defer_style_updates`);
   - cancel checks between chunks;
   - the `retain_emitted_meshes` and instancing gates;
   - S6a's refusal accounting (`refuse_jobs_for_unit` before the pass, `distinct_refusals` after).

   Moving these into `pass.rs`/`finalize.rs` can reorder `on_color_update` vs `on_batch`, or count a refused job twice.

   *Mitigation:* C4-1's ordering test records the full event trace (kind, counts, ids) per corpus file, plus evidence (i) on `ProcessingStats`. 4b is move-only, with no simplification, and lands after S6a.
3. **The cache-reset X changes host-visible lifetimes (C4-11a).** If any host installs `setStyleFinishes`/`setPrepassGeometryFinishes` or the column installers **before** `setEntityIndex` or a `buildPrePass*`, the new reset drops them and finishes or layers silently vanish in the viewer. The worker today installs the index first (`geometry.worker.ts:665-701`), but the finishes path (`style-finishes.ts`) and the sharded finalize (`geometry.worker.ts:1467`) were not fully traced for this note.

   *Mitigation:* C4-11a starts with a trace of every TS call site (viewer, worker, CLI, create oracles, remesh), committed as a test-side sequence fixture. Any slot a host installs before the index moves to the inputs tier instead of being reset. A wasm-contract test loads two files on one `IfcAPI` and asserts no stale finishes, textures or type sets.
