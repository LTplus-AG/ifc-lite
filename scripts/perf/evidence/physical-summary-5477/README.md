# Physical summary work on the browser main thread (#5477)

The candidate narrows the viewer's physical-entity scan to source type buckets, then applies overlay retypes, creations and deletions through the canonical entity iterator. The metadata panel retains the physical membership list until its store, mutation view or version changes. Geometry and WASM code are unchanged.

## Initial controlled cohort (W2)

`protocol.json` identifies the frozen source and production bundles. Five alternating pairs per fixture used a fresh headless Windows Chromium process per sample and observed the same readiness conditions. Each sample ran while competing WSL processes were CPU-limited to four logical CPUs, with automatic restoration at the recorded time. Windows witness and static-server processes ran at High priority. The OS file cache was not purged. `runs.jsonl` retains all 30 samples in execution order, with per-sample raw-result and method SHA-256 hashes; `summary.json` derives the medians and paired changes. Raw files remain in the measurement host's local `physical-summary-5477-prod-w2-*.{json,method.json}` archive, not in this PR because they contain machine paths and model property text.

The measured interval starts when Playwright selects the file and stops when the viewer model is complete, its spatial index and canvas are ready, and the Holter finalization log is observed. The observer polls every 100 ms. A post-readiness GPU pick, canvas click and properties check are excluded from this interval. All ten runs showed 56,697 flat meshes, 755,426 triangles, 60,549 elements with geometry, 2,807,815 total entities, a closed indexed scene target, a GPU hit, a matching selection and visible properties. No page error or unexpected HTTP error occurred; the local analytics script returned the expected 404. Mesh/triangle counts agree, but no byte-level mesh fingerprint was taken. The browser GPU adapter was not recorded by this witness.

The observed base readiness median was **9,641 ms** and the candidate median was **6,815 ms**, a **29.3%** decrease. Every pair improved. Candidate samples ranged from 6,267 to 9,086 ms and all five satisfied the 14-second Holter gate. The base's fifth sample took 22,030 ms and failed that gate; it remains in the cohort and median. Base spread was **143.1%** of its median, above the existing reporter's **20%** noise limit. **The formal performance verdict for this cohort is inconclusive; the qualifying W4 repeat is recorded below.** The variable host busy readings and uncontrolled file cache limit precision. This is a browser readiness observation for this frozen build and host, not a qualified worker geometry speedup or a universal load-time guarantee.

The AC20 control had 317 meshes, 33,356 triangles and 82 elements in all ten runs; its observed readiness median changed 917→878 ms. ISSUE_129 had 1,402 meshes, 134,675 triangles and 969 elements in all ten runs; its observed median changed 2,418→2,431 ms. All 20 controls completed without product page errors and passed the same pick/selection/properties witness. These observations do not repair Holter's excessive base spread.

An earlier one-pair diagnostic crossed a host-load boundary and is **excluded** from the controlled cohort. It must not be pooled with these 30 samples. `unqualified-w3.jsonl` preserves a later ten-sample Holter repeat with Windows affinity `0xFFF000`: its base spread was still 32.3%, above the 20% reporter limit. Four runs produced a complete browser result but the launcher hit an exited-child race after that result, leaving no method JSON. Their `rawMethodSha256` is null; none was fabricated. W3 is also **inconclusive**.

## Qualified Holter repeat (W4)

`qualified-w4.jsonl` records five further alternating Holter pairs. Competing WSL processes were restricted to one logical CPU during the window; Windows server, witness and browser processes used affinity `0xFFF000` and High priority. Every run has an independent pre-load affinity file created **before file input selection**, with the witness/runner SHA and variant. The server-switch timeline independently matches each run's server PID, variant, manifest hash and affinity. All ten browser results passed the same readiness, output-count, closed/indexed target, GPU pick, click-to-properties and error checks. The launcher hit the exact `Chrome process exited during affinity read` error **after** three complete browser results and did not write those method files; their method hashes are explicitly null. Their result files were written 147, 130 and 113 ms before the corresponding launcher failures. The pre-load files and browser results survive and match the served-side timeline. This establishes completed load measurements with subsequent affinity-monitor failures; it does not reconstruct final affinity history for those browser processes. No sample was dropped.

Base readiness was 8,813–10,110 ms (median **9,332 ms**, 13.9% spread of its median), below the existing 20% noise ceiling. Candidate readiness was 6,480–6,740 ms (median **6,650 ms**, 3.9% spread), a **28.7% median reduction**. Every paired comparison improved and all five candidate runs met the 14-second browser gate. This is the qualified Holter browser readiness verdict for these frozen builds under the documented host controls; the AC20 and ISSUE_129 control cohorts above remain separate. W4's WSL affinity window ended with 1,391 threads reported restored. The final audit found zero affinity mismatches across 4,166 live saved-thread checks over four isolation windows.

## Reproduction and provenance

`witness.mts` is a parameterized copy of the production observer, with local machine literals replaced by required environment variables (`WITNESS_CHECKOUT`, `WITNESS_FIXTURE`, `WITNESS_CHROME`, `WITNESS_ORIGIN`, output prefix). It reads the temporary `window.__ifcLiteWitness` bridge; a plain production build cannot run this observer. `main.tsx.probe-tail` is the exact read-only tail appended **identically to both builds** after `mountViewer(...)`. Keep `bootstrap.tsx`'s first two side-effect imports in their original order. Build each frozen viewer, verify `main.tsx` matches the recorded probed SHA, then restore `main.tsx` after creating the snapshots. The bridge was only present in local measurement builds and does not ship. `static-server.mjs` is byte-identical to the local server script and serves frozen `dist` with the required cross-origin headers. `protocol.json` retains source, bridge, served manifest/entry, fixture and matching WASM hashes. The saved local production observer and launcher gained start/load gates and affinity control **after** w2; protocol labels their SHA values post-cohort. The readiness predicate and browser checks are unchanged. No claim of an exact byte-for-byte w2 runner archive is made.

On Windows, build base and candidate production viewer bundles from the recorded sources with the same WASM and temporary bridge. For each row, run `serve-variant.ps1` with the row's `side`, build root, output directory, and port; it starts `static-server.mjs` with cross-origin headers and affinity `0xFFF000`. Then run `run-windows.ps1` with the row's run ID, fixture, variant, checkout, build root, fixture root, Chrome executable, output directory and port. The launcher starts a fresh witness process at High priority, pins it and Chrome children to `0xFFF000`, waits for Chrome before opening the file-input gate, records pre-load affinity and SHA evidence, and restores server priority. The corresponding PowerShell commands are:

```powershell
./serve-variant.ps1 -Variant base -BuildRoot $builds -OutputDir $results -Port 5276
./run-windows.ps1 -Run w4-p1a-holter -Fixture Holter -Variant base `
  -Checkout $checkout -BuildRoot $builds -FixtureRoot $fixtures `
  -ChromePath $chrome -OutputDir $results -Port 5276
```

Set `$builds`, `$checkout`, `$fixtures`, `$chrome`, and `$results` to local paths; the scripts contain no private paths. Switch side in the recorded order, verify each served manifest/entry/WASM hash against `protocol.json`, and run only one owned browser at a time. The host isolation window is external to the Windows scripts and must be separately controlled and recorded. The w2 measured launcher used High priority without the later fixed affinity/load gate, so this command reproduces the stricter W4 protocol, not w2 byte-for-byte. A raw result's `ok` includes the 14-second gate, so the base fifth W2 Holter row has exit code 1 even though its load and functional checks completed.
