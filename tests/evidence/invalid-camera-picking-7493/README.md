# Invalid camera picking (#7493)

The production report contains four unhandled point-selection exceptions after an RTE camera frame became unavailable. This change prevents selection from consuming that unavailable frame; it does not establish what moved the original 615.95 MB production model session beyond the supported envelope.

The regression suite uses the real Camera and PickingManager, with deferred GPU boundaries. Before the change, three invalid-camera admission cases throw and one pending CPU rectangle incorrectly returns old hits. After the change, all 90 focused camera/picking tests pass. The tests also prove picking resumes after a supported pose is restored. Two additional cases cover a camera invalidating and recovering during a pending CPU/point rectangle readback, both when that readback resolves and when it rejects. An invalidation generation rejects those stale results without changing ordinary camera-movement behavior.

Native viewer qualification used the catalogued Archicad FZK fixture on NVIDIA Blackwell WebGPU. With a valid pose, the real GPU pick returned entity 59753 / geometry item 59737. Setting camera X to 1,000,000,001 deliberately invalidated the frame: point picking returned null, rectangle picking returned an empty set, and a real canvas click produced no unhandled rejection. Restoring the original pose returned exactly the same entity, item, and world coordinates, and rendering resumed with 52 draw calls. See `receipt.json` and `recovered.png`.

This is functional qualification, not a performance measurement or a reproduction of the original model's camera trigger. The issue stays open for that trigger and recovery investigation.

The native observations were made against the working renderer change later committed as `2d59c2a7a613e52323467a497db0861e561a007e`, on base `425230a0351681863bbea800c27518850bbc3294`. The receipt now records hashes of those renderer source files. The invalidation-generation repair in `8f24928ba463220f2e56d2a60a040039559f5350` was qualified separately by the 90 focused tests; the earlier screenshot is not native proof of its pending-readback behavior.

Runtime provenance is bounded. The checkout installed the published `@ifc-lite/wasm@10.4.0` runtime with `pnpm build:wasm:fetch`; it did not successfully compile a new WASM runtime for this PR. Retrospective SHA-256 comparison confirms the installed `.wasm` and JavaScript glue match that npm tarball. The parser source tree and runtime file hashes are in the receipt. The original browser-loaded parser modules, renderer modules and WASM response were not hashed at capture time, and subsequent typechecking rebuilt parser `dist`. Their exact historical browser artifact identity is therefore unrecorded. This receipt supports the observed native functional result with the stated limitation; it does not attest a reproducible final-head browser build or qualify the original production model.
