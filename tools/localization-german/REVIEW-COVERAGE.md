# German catalogue coverage and maintenance review

Independent LLM review, 2026-11-05, working tree over HEAD `f6ffa4fc655d6ec29c3c8f0baaaacde76bb4899f`. This is not native-speaker approval. Read root/viewer AGENTS, machine/fleet guidance, ACCEPTANCE.md, the i18n maintenance instructions, the new test, validator, registry, activation and lazy metadata. Only this report was written. No delegation, builds, test-suite execution, commits, or campaign changes. Small read-only Node/tsx inspections imported actual catalogue objects; counts below are intermediate observations during concurrent translation.

## Findings and precise fixes

1. **Major: the German test masks startup rejection of lazy retained-geometry translations.** `german-catalogue.test.ts:28` calls `registerEnglish(english)` before validation. `catalogue-problems.ts` recognizes keys through the eager `en` object or `lazyMessageParameters`; registration mutates that same eager object. Consequently the test validates a different registry state from a fresh browser startup. In a fresh Node process, `checkCatalogue(de)` reported **98** problems, all retained-geometry keys, beginning with `retainedGeometry.shapeOnlyReason`. After registering every English feature, the same inspection reported zero problems. `lazy-catalogue-shape.ts` has no retained-geometry shape. `createLocaleActivator` drops rejected messages before registering German; loading the English feature later cannot restore those discarded German messages. This affects startup before retained feature registration, particularly the lazy feature configuration.

   Fix: add exact retained-geometry startup key/placeholder metadata to the existing lazy validation mechanism. Add a fresh-registry regression that activates the real German catalogue before registering lazy English, asserts ownership and German resolution of a retained key, then registers the real English feature and asserts German remains active. Keep the full loaded-object parity test, but isolate its English registration from startup tests (a fresh process or separate isolated test file). Assert startup `checkCatalogue(de).problems` is empty before enrichment. The present negotiation test runs after enrichment and asserts locale/lang/storage only, so it cannot detect translations silently discarded during activation.

2. **The explicit exceptions include false justifications, which the length-only reason assertion accepts.** The 387-entry draft is explicit and value-pinned, which is good, but `measure.polyline.indexLabel` (`Poly #{index}`) and `sectionTool.parked.labelBox` (`Box · {x}×{y}×{z} m`) claim to contain only runtime placeholders, mathematical notation and unit symbols. `Poly` and `Box` are literal UI labels. Callers `MeasurementList.tsx:111` and `SectionParkedChip.tsx:62` display these as measurement/section labels; they are neither model-supplied names nor IFC EXPRESS identifiers. `properties.landXmlSource.parcelStatus` (`Status: {status}`), `properties.materialTotals.fallbackName` (`Material #{id}`), `properties.material.materialN` (`Material {n}`), and `repositionPanel.axisFieldDeltaAriaLabel` (`Delta {axis}`) likewise need reasons acknowledging their literal German words/notation rather than pretending the words are placeholders or units.

   Fix each reason according to the actual label. For `Box`, document the intentionally retained German technical term for the section box, or use `Schnittbox` and remove its identical-copy exception. For `Poly`, use `Polylinie #{index}` and remove the exception unless the maintainer can establish a specific intentional shared abbreviation. For Status/Material/Delta, an explicit same-spelling German-term reason is sufficient. Keep the exact key/value allowlist; do not replace it with capitalization/CamelCase inference. Reason length is only a minimal formatting check and must not be described as semantic approval. No arbitrary untranslated English sentence was established among the 387 draft exceptions.

3. **Acceptance and maintenance prose incorrectly prohibit the intentional empty count suffix.** ACCEPTANCE.md says “No empty messages”; the i18n README says the test “rejects empty messages”. The test correctly exempts only `modelingCommand.unit.count` when English is also empty. This is a deliberate dimensionless unit suffix, not a missing translation (`catalogues/modeling-command.en.ts:16`). Fix both instructions to state this exact exception and keep the runtime value `''`. Do not translate it to a word or introduce a broad empty-message exemption.

## Current integration observations, not additional translation defects

- The first loaded-object snapshot contained 10,607 English keys and 10,064 German keys; German had no unknown keys, all 387 existing exceptions were still identical and value-correct, and the only empty message was the intentional count suffix. That snapshot's German feature aggregate and `de.ts` were identical. These are metadata observations, not a passing suite: translation was still in progress and the equality assertion would fail on missing keys.
- A later file/export inspection found the newly arrived `misc-panels-b.ts` exporting `miscPanelsBDe` absent from both the imports and spreads of `de.ts`; `appearance-workflows.en.ts` was still awaiting its German sibling at that instant. Regenerate `de.ts` after translators finish, then compare the loaded shipping entry with all German feature objects, as well as with all English keys. This is expected draft assembly work, not a separate naming defect. Other inspected German export names matched the entry imports; no Russian text was found in the inspected feature modules. Do not copy the Russian entry's import paths/type-relative paths without adapting them.
- The directory-driven `allEnglish()` includes lazy catalogues rather than maintaining a fragile eager-only list. Exact key parity, placeholder validation, value-pinned exception membership, nonempty checks, actual plural resolution and Intl formatting are meaningful behavior/data checks. The map storage and plain `lang` target exercise the real activator logic; they do not establish browser/Vite discovery, DOM accessibility or rendered layout acceptance.
- `checkCatalogue` compares placeholder unions over plural forms. It does not prove every selected form carries every required non-count parameter. The inspected German plural objects showed no missing non-count parameters relative to the corresponding English forms. For future stronger regression coverage, exercise the actual resolver for German `one` and `other` with sentinel parameters for every plural message; do not require `{count}` in a singular form where a spelled-out singular is intentional.

## Schema protection and exception decisions

No blanket CamelCase rule is justified. `properties.extrusion.profile` = `SweptArea` and `.profileType` = `ProfileType` describe real source fields in `ExtrusionInspection.tsx:73,87`; `properties.sweptDisk.innerRadius` = `InnerRadius` labels the actual `occurrence.InnerRadius` in `SweptDiskInspection.tsx:58`. Preserve them. Likewise preserve `roomReview.PredefinedType`, `roomReview.ObjectType`, `IfcSpace.ObjectType`, `GlobalId`, attribute-input examples `Description, ObjectType, Tag, …`, and `Pset_WallCommon.FireRating` selector syntax: these identify schema fields or machine-consumed query examples, not ordinary prose. New exceptions for `InnerRadius` and similar completed files should state that concrete field identity.

`chatByok.keyModal.walkthroughStep2CreateKey` = `Create Key` is displayed in bold inside instructions directing users to an external provider UI (`ByokKeyModal.tsx:256`); retaining the external control label is defensible, but its reason should say that rather than the generic identifier/product/format/shortcut disjunction. `Flow`/`Flows` refer to the application's named workflow feature; explain that intentional feature terminology if retained. Name/Status/Filter/Material/Radius and format/brand/unit/shortcut values are not evidence of untranslated prose just because English shares their spelling.
